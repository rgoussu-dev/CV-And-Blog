    Security in Java applications — the map

    # How the recurring security concerns map onto Spring Security, Quarkus and Micronaut modules and the standards behind them.

    Conceptsaved 2026-08-09 #java#security#frameworks#spring#quarkus#micronaut

    Overview

    Security in a Java application is rarely invented; it is assembled. The concerns are the same everywhere — who is calling (authn), what they may do (authz), the OAuth2/OIDC protocol family, the web attack surface, cryptography and secrets, and the platform's own hardening — and each major framework ships a security stack that implements the relevant standards. This note maps concern → standard → framework module, and hands off to the deep dives. General theory (threat models, protocol semantics, crypto principles) lives in the Security theme; here we only care how it lands in Java code.

    Key points

    • Authn vs authz: every stack separates establishing an identity (filters/interceptors producing a SecurityContext/Authentication) from enforcing permissions (URL rules, @RolesAllowed/@PreAuthorize-style annotations, method interceptors).
    • OAuth2/OIDC is the default perimeter: resource-server JWT validation for APIs, OIDC login for browser apps, an external IdP (usually Keycloak) as authorization server — see OAuth2 & OIDC in Java.
    • The web attack surface (injection, XSS, CSRF, CORS, headers, deserialization) is partly framework-handled, partly your job — see Web security.
    • Crypto & secrets: the JDK's JCA/JSSE providers plus Bouncy Castle, and Vault-style external secret stores — see Cryptography in Java.
    • Platform security: keep the JDK patched (CPU releases quarterly); the old SecurityManager is deprecated for removal and no longer a sandboxing answer — process isolation and containers are.
    • Spring Security is filter-chain based (SecurityFilterChain beans); Quarkus builds on Elytron/SmallRye plus per-concern extensions; Micronaut Security uses compile-time AOP rules — same concepts, different wiring.
    • Supply chain: dependency scanning, SBOMs and the tooling around them are covered in Security testing, not here.

    Jakarta Security

    For completeness: Jakarta EE defines its own portable security API — Jakarta Security (HttpAuthenticationMechanism, IdentityStore), Jakarta Authentication (JASPIC lineage) and Jakarta Authorization (JACC lineage) — implemented by full EE servers such as WildFly, Payara and Open Liberty. In practice the three frameworks above ship their own richer stacks and only borrow the annotations (@RolesAllowed et al.); you meet Jakarta Security proper mainly on classic application servers.
