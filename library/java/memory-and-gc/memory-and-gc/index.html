    Java memory & garbage collection — the map

    # The map of Java memory — where objects live, the lifecycle from allocation to reclamation, and how the memory-model and GC notes fit together.

    Conceptsaved 2026-08-09 #java#jvm#memory#gc#internals

    Overview

    "Java manages memory for you" hides two separate contracts. The first is spatial and temporal: where bytes live (heap, stacks, metaspace) and when they are reclaimed — the garbage collector's territory. The second is ordering: what one thread is guaranteed to observe of another thread's writes — the Java Memory Model, which despite the name has nothing to do with layout and everything to do with concurrency. This group covers both, from the runtime's memory anatomy through GC theory to the concrete collectors and their trade-offs.

    Key points

    • Two contracts, one word: memory management (allocation & GC) and the memory model (visibility & ordering, the JMM) are unrelated mechanisms that share a name — conflating them is the classic interview stumble.
    • Object lifecycle: allocation in a thread-local buffer (bump-the-pointer, ~10 instructions) → survival through young collections → promotion to the old generation → reclamation when unreachable; most objects never get past the first step.
    • The JVMS deliberately leaves GC open: the spec defines the runtime data areas but not how they are collected — which is why HotSpot alone ships six collectors and other implementations (OpenJ9, Azul) compete on theirs.
    • The trade-off triangle: throughput, latency (pause times), footprint — every collector picks two; there is no best GC, only a best fit for a workload.
    • The reading order for this group: memory anatomy (where things live) → the JMM (what threads observe) → GC principles & algorithms (how reclamation works in theory) → the collectors compared (what to actually pick and tune).
    • Observe before tuning: -Xlog:gc*, jstat, jmap and JFR tell you what the GC is doing; flags come after evidence, never before.
