    Testing in Java — strategies & tooling map

    # Map of Java testing strategies — unit to security — with the standard tools for each and links to the deep-dive notes.

    Conceptsaved 2026-08-09 #java#testing#tooling#quality

    Overview

    The Java ecosystem has a mature, largely framework-agnostic testing stack: JUnit 5 as the universal engine, a specialist library per concern layered on top, and first-class test support baked into Spring, Quarkus and Micronaut. This note maps the strategy axes — unit, integration, end-to-end, mutation, property-based, performance, security — onto the tools worth knowing, and hands off to a deep-dive note per strategy.

    Key points

    • JUnit 5 is the substrate: Spring Test, @QuarkusTest and @MicronautTest are all Jupiter extensions — one engine, one IDE/build integration, whatever the framework.
    • House position — test behaviour at the right boundary: pick the outermost boundary that still gives fast, deterministic feedback; couple tests to observable behaviour, not to implementation structure, or every refactor breaks the suite.
    • Pyramid vs trophy: the classic pyramid (many unit, fewer integration, few E2E) optimises for speed; the "testing trophy" argues integration tests catch the most real bugs per test now that Testcontainers makes them cheap. In practice: mostly-unit for domain logic, mostly-integration for glue-heavy services — the shape follows the code.
    • Coverage is a floor, not a goal: line coverage says what ran, mutation testing (PIT) says what was actually asserted.
    • Example-based tests miss whole input classes: property-based testing (jqwik) complements them with generated inputs and shrinking.
    • Performance and security are testing concerns too: JMH/Gatling and dependency-check/ZAP belong in the same portfolio, not in a separate silo.

    Details

    Strategy → tools → deep dive

    Strategy What it verifies Standard Java tools Deep dive
    Unit One behaviour in isolation, milliseconds JUnit 5, Mockito, AssertJ Unit testing
    Integration Code + real dependencies (DB, broker, HTTP) Testcontainers, Spring test slices, @QuarkusTest, @MicronautTest, WireMock Integration testing
    End-to-end The deployed system through its public surface REST Assured, Selenium/Playwright, Karate; Pact for the contract alternative End-to-end testing
    Mutation Quality of the test suite itself PIT (pitest) Mutation testing
    Property-based Invariants over generated inputs jqwik (QuickTheories, junit-quickcheck legacy) Property-based testing
    Performance Latency/throughput of code and system JMH (micro), Gatling/k6/JMeter (load), JFR alongside Performance & load testing
    Security Known vulns, insecure code, runtime exposure OWASP dependency-check/Snyk, SpotBugs+FindSecBugs, OWASP ZAP, Jazzer Security testing

    Choosing the boundary

    • Pure domain logic → unit tests, no framework, no mocks beyond the domain's own ports.
    • Persistence/messaging/HTTP glue → integration tests against the real thing in a container; mocking a database proves nothing about SQL.
    • Cross-service behaviour → prefer consumer-driven contracts over broad E2E; keep a thin smoke layer of true E2E for deployment confidence.
    • Suite trustworthiness → run PIT on the modules where correctness matters most.
