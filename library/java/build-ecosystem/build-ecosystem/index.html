    The Java build ecosystem

    # The three ways to build Java — bare JDK tools, Maven, Gradle — and the artifact formats they produce.

    Conceptsaved 2026-08-09 #java#build#tooling#packaging

    Overview

    Every Java build ultimately does the same thing: compile sources with javac, arrange the classes and resources into an artifact, and resolve the third-party jars the code depends on. The ecosystem offers three tiers for orchestrating that: the bare JDK tools, Maven (convention-first, declarative), and Gradle (flexible, programmable). All three resolve dependencies against the same substrate — Maven Central and Maven-repository metadata — so the choice is about build orchestration, not about a separate package universe.

    Key points

    • Bare JDK tools: javac compiles, jar packages, jlink assembles a trimmed runtime image and jpackage wraps it as an installer. Fine for scripts, teaching, and single-file programs; unmanageable once dependencies appear.
    • Maven: fixed lifecycle, XML POM, convention over configuration. The conservative, predictable default — see Maven deep dive.
    • Gradle: a task graph driven by build scripts (Groovy or Kotlin DSL), incremental and cacheable. The default for Android and large multi-project builds — see Gradle deep dive.
    • Shared substrate: both resolve GAV-coordinated dependencies from Maven Central (plus private repositories); an artifact published from either is consumable by both.
    • Wrappers (mvnw, gradlew): committed launcher scripts that download and pin the build-tool version, so a clone builds without any locally installed Maven/Gradle. Use them; never depend on a machine-global installation.
    • Newer entrants, one line each: Bazel (monorepo-scale, hermetic), Mill (Scala-ish, fast), jbang (single-file scripting with dependencies) — niche, worth knowing they exist.

    Details

    Artifact formats

    Format Contains Consumed by Relevance today
    jar Classes + resources + META-INF/MANIFEST.MF Other builds (as a dependency), classpaths The universal unit; every library ships as one
    executable jar jar with Main-Class in the manifest java -jar app.jar Common for small tools; needs its dependencies alongside
    fat/shaded jar App + all dependencies merged into one jar (shading may rename packages) java -jar, container images The de-facto deployable for Spring Boot & friends (Boot uses a nested-jar variant)
    war Web app layout (WEB-INF/classes, WEB-INF/lib) Servlet containers (Tomcat, Jetty) Fading — embedded servers in fat jars won
    ear Multiple wars/jars + application.xml Full Jakarta EE application servers Legacy; new work rarely targets it
    jmod Module classes + native libs/config for linking jlink at link time only JDK-internal packaging; not a runtime format
    jlink runtime image Custom trimmed JDK + application modules End users / container images Small self-contained runtimes; feeds jpackage
    native executable AOT-compiled machine code (GraalVM native-image) OS directly — no JVM install Growing: serverless & CLI tools where startup/memory dominate

    Choosing

    • Convention vs flexibility: Maven gives you one blessed project shape and lifecycle — every Maven project looks alike, at the cost of fighting the model when you deviate. Gradle lets the build be programmed — powerful, at the cost of builds that must themselves be maintained like code.
    • Ecosystem defaults: libraries and conservative teams default to Maven (stable, lowest-surprise, ubiquitous CI support); Android mandates Gradle, and large multi-module builds tend to justify Gradle's incrementality and caching.
    • Either is a fine default; switching costs are real, so pick per-organisation, not per-project fashion.
