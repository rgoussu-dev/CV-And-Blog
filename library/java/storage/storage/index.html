    Storage access from Java — the map

    # How Java reaches every storage kind — drivers, mapping layers, and the Spring, Quarkus, and Micronaut integrations for each.

    Conceptsaved 2026-08-09 #java#storage#databases#frameworks#spring

    Overview

    Java talks to storage through a consistent three-layer stack, whatever the store: a driver (wire protocol client), an optional mapping/ORM layer (objects ↔ rows/documents/nodes), and a framework data layer (Spring Data, Quarkus Panache, Micronaut Data) that adds repositories, transactions, and configuration. Knowing which layer a problem lives in — and which concrete library fills each slot for a given store — is most of the craft. This note maps the landscape by storage kind and hands off to the deep dives.

    Key points

    • Three layers everywhere: driver → mapping/ORM → framework data layer. Each is optional above the driver; every abstraction you add trades control for convenience.
    • Relational is the standardized case: JDBC is a real standard, JPA a real mapping standard. Everything else is de-facto: each NoSQL store has a vendor driver, and Spring Data is the closest thing to a common repository idiom across them.
    • Framework data layers differ in mechanism: Spring Data generates repository implementations at runtime via proxies; Micronaut Data does it at compile time (no reflection, GraalVM-friendly); Quarkus Panache leans on build-time bytecode transformation.
    • Reactive is a separate lane: R2DBC for relational, reactive driver variants for MongoDB, Lettuce for Redis — don't mix blocking drivers into reactive pipelines.
    • TimescaleDB and QuestDB blur categories: both speak PostgreSQL wire protocol, so the entire JDBC stack applies unchanged to a time-series store.
    • Search and object storage sit apart: Elasticsearch and S3 have their own clients and no ORM analogue; they get one-line rows below, not deep dives.

    Choosing an entry point

    • Start at the driver docs when debugging connectivity, timeouts, or serialization; start at the framework layer when wiring configuration, pooling, health checks, and metrics — Boot/Quarkus/Micronaut all auto-configure the driver from properties.
    • Testcontainers is the common test substrate for every row of the table: real store, real driver, in CI.
