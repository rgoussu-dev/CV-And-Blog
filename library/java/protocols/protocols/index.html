    Backend protocols in Java — the map

    # How the main service protocols — REST, GraphQL, gRPC, WebSockets/SSE, messaging — map onto Jakarta, Spring, Quarkus and Micronaut.

    Conceptsaved 2026-08-09 #java#protocols#frameworks#api-design

    Overview

    Protocol choice shapes a Java service more than most design decisions: it fixes whether calls are synchronous request/response or asynchronous fire-and-forget, whether the wire format is human-readable text or a binary schema, and whether the interaction is a single exchange or a long-lived stream. Each protocol arrives in the JVM ecosystem twice over — once as a standard or de-facto spec (Jakarta REST, GraphQL, gRPC, Jakarta WebSocket, Jakarta Messaging) and once per framework as the Spring, Quarkus and Micronaut integration of that spec. Knowing both layers is what lets you move between stacks without relearning the protocol.

    Key points

    • Sync vs async: REST, GraphQL and gRPC unary calls are request/response; messaging decouples producer from consumer in time; WebSockets/SSE hold a connection open for server push. Pick per interaction, not per service — most systems mix them.
    • Text vs binary: JSON over HTTP (REST, GraphQL) is debuggable and universally consumable; protobuf (gRPC) and Avro (Kafka) are compact, fast and schema-enforced but need tooling to inspect.
    • Contract location: REST contracts are documented after the fact (OpenAPI); GraphQL and gRPC are schema-first by construction (SDL, .proto); messaging contracts live in a schema registry if they live anywhere. The doc tooling per stack has its own note: API documentation in Java.
    • Spec vs framework: the standard defines annotations and semantics (Jakarta REST, Jakarta WebSocket, Jakarta Messaging, MicroProfile GraphQL); Spring historically ships its own equivalent APIs, while Quarkus and Micronaut mostly implement or wrap the standards.
    • Streaming is the differentiator: only gRPC, WebSockets/SSE and messaging handle server push and long-lived flows naturally; forcing streaming through REST means polling.
    • Every deep dive below names the concrete library per stack — that mapping is the point of this group.

    Choosing

    Default to REST for public and browser-facing APIs; reach for GraphQL when clients need flexible aggregation over many resources; gRPC for internal service-to-service calls where latency, streaming or polyglot contracts matter; WebSockets/SSE when the server must push; messaging whenever the work can be asynchronous — which is more often than request/response habits suggest. The deep dives cover the trade-offs per protocol.
