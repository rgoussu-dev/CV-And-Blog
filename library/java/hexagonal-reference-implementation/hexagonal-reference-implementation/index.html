    Hexagonal architecture reference implementation — Java

    # The house layout for a hexagonal monolith/microservice in Java — Maven multi-module, application/domain/infrastructure trisection, one deployment unit per primary adapter.

    Conceptsaved 2026-08-09 #hexagonal-architecture#architecture#java#maven#modules#reference-implementation

    Overview

    The house reference implementation of hexagonal architecture for Java — an opinionated layout, not a survey of what the internet does. The shared, language-agnostic principles live in that note; this group realizes them for Java with Maven multi-module as the enforcement mechanism. The per-layer implementation guidelines live in the notes of this group: application, domain, infrastructure, deployment & IaC.

    Key points

    • Three top-level folders per service: application/ (primary adapters), domain/ (the hexagon), infrastructure/ (secondary adapters) — plus deployment/ for IaC.
    • One primary adapter = one deployment unit = one container. Each user-side adapter under application/ (a REST API, a gRPC server, a Kafka consumer group, a cron runner) carries an implementation module and — where the transport contract is real and consumable (REST DTOs/OpenAPI, gRPC protos, Kafka schemas) — a separate API module (DTOs + contracts). A cron runner has no consumable contract and stays a single module: the pair is earned by a contract, not imposed for symmetry.
    • The domain is two modules: domain-api (the surface API — ports, command DTOs, domain events) and domain-core (the actual implementation). Everything else depends on domain-api; almost nothing depends on domain-core.
    • Infrastructure granularity is an ad-hoc, per-context decision — a single module or several granular ones (one per port × technology), the forcing question being which deployment units need which driven adapters; ubiquitous ports (clock, id generation) sit together in a commons module (see infrastructure layer for the forces).
    • An optional configurator module harbors the wiring of domain and infrastructure modules, so deployment units assemble rather than wire.
    • Containerisation definitions live with their deployment unit — the Dockerfile sits next to the implementation module it packages, never in a central docker/ folder.
    • Every directory/module carries a README.md and an AGENTS.md stating its purpose and the conventions applicable at that location.
    • The module graph is the architecture. Maven's dependency graph makes the dependency rule (domain-api depends on nothing; everything points inward) compile-time-enforced, backed by the enforcer plugin and ArchUnit.

    Details

    The reference tree

    acme-service/
├── README.md                          # what the service is, how to build & run
├── AGENTS.md                          # repo-wide conventions
├── pom.xml                            # parent aggregator (packaging: pom)
├── application/
│   ├── AGENTS.md
│   ├── rest-public/                   # primary adapter → 1 deployment unit
│   │   ├── rest-public-api/           #   DTOs + contracts (OpenAPI, request/response types)
│   │   └── rest-public-app/           #   controllers, mappers, main class
│   │       ├── Dockerfile
│   │       └── README.md
│   ├── rest-backoffice/               # second REST adapter, same shape
│   ├── grpc-server/                   # gRPC adapter (api = proto/generated stubs)
│   ├── kafka-consumers/               # Kafka consumer group adapter (api = message schemas)
│   ├── cron-jobs/                     # single -app module: no consumable contract, no -api
│   └── configurator/                  # optional: wiring of domain + infrastructure
├── domain/
│   ├── AGENTS.md
│   ├── domain-api/                    # ports, command DTOs, domain events
│   └── domain-core/                   # entities, value objects, port implementations

│   ├── AGENTS.md
│   ├── commons/                       # ubiquitous ports: clock, id generation
│   ├── persistence-postgres/          # one module per (port × technology)
│   ├── messaging-kafka/
│   └── client-billing/
└── deployment/                        # IaC — OpenTofu stacks per environment
    ├── AGENTS.md
    └── …

    Dependency rules

    Module May depend on Never on
    domain-api nothing (JDK only) anything
    domain-core domain-api frameworks, infra, application
    infrastructure/* domain-api + its own technology domain-core, other infra modules, application
    application/*-api nothing domain-side (transport contracts only) domain-core, infra
    application/*-app its *-api, domain-api, configurator (or domain-core + chosen infra) other deployment units
    configurator domain-api, domain-core, infrastructure/* application/*

    Dependencies always point inward; the only module allowed to see both domain-core and infrastructure is the configurator (or, without one, each *-app's wiring class).

    Documentation convention

    Each directory/module's AGENTS.md states: what belongs here, what must never end up here, and the local conventions (naming, mapping, testing). The README.md is for the human skimming the tree: purpose, how to build, how to run. The parent README.md links down; the leaf ones link up.

    Examples

    Parent aggregator with the enforcer keeping the graph honest:

    <project>
  <groupId>com.acme</groupId>
  <artifactId>acme-service</artifactId>
  <packaging>pom</packaging>
  <modules>
    <module>domain/domain-api</module>
    <module>domain/domain-core</module>
    <module>infrastructure/persistence-postgres</module>
    <module>infrastructure/messaging-kafka</module>
    <module>application/configurator</module>
    <module>application/rest-public/rest-public-api</module>
    <module>application/rest-public/rest-public-app</module>
    <!-- … one pair (or lone -app, when there is no consumable contract) per primary adapter -->
  </modules>
  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-enforcer-plugin</artifactId>
        <executions>
          <execution>
            <goals><goal>enforce</goal></goals>
            <configuration>
              <rules>
                <bannedDependencies>
                  <!-- overridden per module: domain-api bans everything,
                       infra bans domain-core, apps ban each other -->
                </bannedDependencies>
              </rules>
            </configuration>
          </execution>
        </executions>
      </plugin>
    </plugins>
  </build>
</project>

    domain-api's POM stays deliberately empty of dependencies:

    <project>
  <parent>
    <groupId>com.acme</groupId>
    <artifactId>acme-service</artifactId>
    <version>${revision}</version>
    <relativePath>../../pom.xml</relativePath>
  </parent>
  <artifactId>domain-api</artifactId>
  <!-- no <dependencies>: the contract depends on the JDK alone -->
</project>

    An ArchUnit guard in domain-core's tests, for the rules Maven can't see (package-level leaks inside a module):

    @AnalyzeClasses(packages = "com.acme")
class ArchitectureTest {
    @ArchTest
    static final ArchRule domainIsFrameworkFree =
        noClasses().that().resideInAPackage("com.acme.domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("org.springframework..", "jakarta.persistence..");
}
