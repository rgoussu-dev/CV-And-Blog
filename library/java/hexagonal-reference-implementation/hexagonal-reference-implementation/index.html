    Hexagonal architecture reference implementation — Java

    # The house layout for a hexagonal service in Java — a Maven/Gradle modulith whose module graph is the architecture, one hexagon per bounded context under modules/, composed into runnable assemblies under application/.

    Conceptsaved 2026-08-09updated 2026-08-14 #hexagonal-architecture#architecture#java#maven#modules#modulith#reference-implementation

    Overview

    The house reference implementation of hexagonal architecture for Java — an opinionated layout, not a survey of what the internet does. The shared, language-agnostic principles live in that note; this group realizes them for Java with the build tool's module graph as the enforcement mechanism. The favored shape is a modulith: one hexagon per bounded context under modules/, shared plumbing under platform/, and runnable assemblies under application/. Java is the language where this costs the least — a module is a directory plus a build file, and every dependency rule below is a compile error rather than a convention. The per-layer implementation guidelines live in the notes of this group: user-side & assemblies, domain, infrastructure, module composition, deployment & IaC.

    Key points

    • Three top-level folders: modules/ (one hexagon per bounded context), platform/ (shared, domain-agnostic modules — kernel first among them), and application/ (the assemblies) — plus deployment/ for IaC.
    • One deployment unit per delivery typology, not per adapter. application/api, application/consumer, application/cron are the runnable, containerised artifacts; each mounts the matching user-side adapters of every module it assembles. A module's own adapters are libraries and are never runnable on their own.
    • A module is a whole hexagon: user-side/ (driving adapters), domain/contract + domain/core (the hexagon proper), infra/ (driven adapters). The trisection did not go away — it is now per context instead of per repository.
    • platform/kernel is the dispatch vocabulary — Command, Query, Handler, Mediator — and depends on nothing. Each module gets its own mediator over its own handlers; there is no repository-wide command bus.
    • The one legal inter-module edge is infra → peer user-side/service. A module needing a peer declares a driven port in its own vocabulary and implements it in infra/ by delegating to the peer's in-process service adapter. Everything about carve-out follows from this — see module composition.
    • An adapter's API artifact exists only where the contract is real: the contract/ + adapters/ pair under user-side/api/ is earned by a consumable transport contract (REST DTOs/OpenAPI, gRPC protos, message schemas). A cron adapter is one module.
    • Infrastructure granularity is an ad-hoc, per-context decision — one infra module or one per (port × technology); the forcing question is which assemblies need which driven adapters. Ubiquitous ports (clock, id generation) are not a module's business: they live in platform/ (see infrastructure layer).
    • The assembly is the only place allowed to see a domain/core. It wires domains to infrastructure, binds each driven port to a chosen adapter, and decides which modules share a process.
    • Containerisation definitions live with their assembly — the Dockerfile sits next to the application/<typology> module it packages, never in a central docker/ folder.
    • Every directory/module carries a README.md and an AGENTS.md stating its purpose and the conventions applicable at that location.
    • The module graph is the architecture. Gradle/Maven make the dependency rule compile-time-enforced, backed by the enforcer plugin and ArchUnit; Gradle's implementation versus api configurations additionally stop a module's internals leaking onto a consumer's compile classpath.

    Details

    The reference tree

│   ├── AGENTS.md

│   │   │   │   └── adapters/              #   resources/controllers + mapping

│   └── cron/                              # deployment unit: scheduler assembly
├── compose.yaml
└── deployment/                            # IaC — OpenTofu stacks per environment
    ├── AGENTS.md
    └── …

    Maven artifactIds flatten the path with dashes — ordering-domain-contract, ordering-user-side-api-adapters, platform-kernel, application-api — so the artifact name states the module's address. Gradle project paths do it natively (:modules:ordering:domain:contract).

    Dependency rules

    Module May depend on Never on
    platform/kernel nothing (JDK only) anything
    platform/* (other) platform/kernel any modules/*, any application/*
    modules/x/domain/contract platform/kernel frameworks, infra, user-side, any other module
    modules/x/domain/core its own domain/contract, platform/kernel frameworks, infra, user-side, any other module
    modules/x/infra/* its own domain/contract, peer user-side/service, its technology its own domain/core, any other module's domain, application/*
    modules/x/user-side/api/contract nothing domain-side (transport contracts only) any domain module, infra
    modules/x/user-side/api/adapters its own user-side/api/contract + domain/contract its own domain/core, other modules
    modules/x/user-side/service its own domain/contract its own domain/core, other modules
    application/<typology> anything it assembles another assembly

    Dependencies always point inward, and across modules they point at a peer's user-side only. The assembly is the single module allowed to see both a domain/core and an infrastructure module — the configurator role of the flat layout, now per deployment unit by construction.

    Starting flat, and promoting later

    A service with a single bounded context may skip modules/ and put domain/contract, domain/core, infra/ and user-side/ at the root — the flat trisection, which is this layout with the module level elided. Promotion when a second context appears is mechanical: move the four directories under modules/<first-context>/, add the new module beside it, and update the build's module list. No source file changes, because no source file ever named the layout.

    The reverse warning holds too: do not create modules/ with one module and call it future-proofing. The nesting costs a level of navigation and buys nothing until a second context exists.

    Documentation convention

    Each directory/module's AGENTS.md states: what belongs here, what must never end up here, and the local conventions (naming, mapping, testing). The README.md is for the human skimming the tree: purpose, how to build, how to run. The parent README.md links down; the leaf ones link up.

    Examples

    Parent aggregator with the enforcer keeping the graph honest:

    <project>
  <groupId>com.acme</groupId>
  <artifactId>acme-service</artifactId>
  <packaging>pom</packaging>
  <modules>
    <module>platform/kernel</module>
    <module>platform/commons</module>
    <module>modules/ordering/domain/contract</module>
    <module>modules/ordering/domain/core</module>
    <module>modules/ordering/infra/persistence-postgres</module>
    <module>modules/ordering/user-side/api/contract</module>
    <module>modules/ordering/user-side/api/adapters</module>
    <module>modules/ordering/user-side/service</module>
    <!-- … the same block per bounded context … -->
    <module>application/api</module>
  </modules>
  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-enforcer-plugin</artifactId>
        <executions>
          <execution>
            <goals><goal>enforce</goal></goals>
            <configuration>
              <rules>
                <bannedDependencies>
                  <!-- overridden per module: kernel bans everything, a domain bans
                       every other module, infra bans its own core, assemblies ban
                       each other -->
                </bannedDependencies>
              </rules>
            </configuration>
          </execution>
        </executions>
      </plugin>
    </plugins>
  </build>
</project>

    platform/kernel's POM stays deliberately empty of dependencies:

    <project>
  <parent>
    <groupId>com.acme</groupId>
    <artifactId>acme-service</artifactId>
    <version>${revision}</version>
    <relativePath>../../pom.xml</relativePath>
  </parent>
  <artifactId>platform-kernel</artifactId>
  <!-- no <dependencies>: the dispatch vocabulary depends on the JDK alone -->
</project>

    ArchUnit guards in the assembly's tests, for the rules the build graph can't see (package-level leaks inside a module, and cross-context package imports):

    @AnalyzeClasses(packages = "com.acme")
class ArchitectureTest {
    @ArchTest
    static final ArchRule domainIsFrameworkFree =
        noClasses().that().resideInAPackage("com.acme..domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("org.springframework..", "jakarta.persistence..");

    @ArchTest
    static final ArchRule contextsMeetOnlyAtTheServiceSeam =
        SlicesRuleDefinition.slices()
            .matching("com.acme.(*)..")           // one slice per bounded context
            .namingSlices("context $1")
            .should().notDependOnEachOther()
            .ignoreDependency(
                resideInAPackage("com.acme..infra.."),
                resideInAPackage("com.acme..userside.service.."));
}
