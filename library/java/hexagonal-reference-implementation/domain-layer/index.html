    Domain layer — contract & implementation

    # Two modules — domain-api with the surface API of the domain (ports, command DTOs) and domain-core with the actual implementation — and the rules for what crosses that line.

    Conceptsaved 2026-08-09 #hexagonal-architecture#architecture#java#domain#ports

    Overview

    The domain/ folder is the hexagon itself, split in two modules: domain-api, the surface API of the domain — ports, command DTOs, domain events, result types — and domain-core, the actual implementation — entities, value objects, domain services. The split is what lets every other module depend on the domain contract while almost none touch the implementation: adapters and infrastructure compile against domain-api; only the configurator (or the wiring code) ever sees domain-core.

    Key points

    • domain-api depends on nothing — JDK only. No framework, no annotation, no logging facade. It is the most stable artifact in the service; every dependency arrow in the build points at it.
    • Both port directions live in domain-api: driving ports (the use-case interfaces primary adapters call) and driven ports (the interfaces infrastructure implements). Driven ports must sit in the contract module, not in core — otherwise infrastructure modules would need domain-core to compile, and the whole layering collapses.
    • Boundary types, not entities, cross the line. Commands, queries, results and events in domain-api are dedicated types (records, ideally). Entities and value objects stay internal to domain-core — they are the domain's working state, not its published vocabulary. When a driven port genuinely needs a rich domain type in its signature, that type moves to domain-api deliberately — a design decision, not a default.
    • domain-core depends only on domain-api and implements its driving ports. Framework-free: constructor injection of driven ports, plain Java, exhaustively unit tested without any container.
    • Transaction boundaries are a domain decision expressed as a port (e.g. a TransactionRunner driven port, or unit-of-work semantics on the repository port) and implemented in infrastructure or decorated in the configurator. @Transactional on a controller is the smell to avoid.
    • One domain, many adapters. The domain pair is shared by every deployment unit; a unit that uses only a slice of the use cases still depends on the whole domain-api — slicing the domain itself is a service boundary question, not a module one.

    Details

    What goes where

    Artifact Module Notes
    Driving ports (use-case interfaces) domain-api e.g. PlaceOrder, CancelOrder — one per use case or grouped per aggregate, house style is per use case
    Driven ports domain-api e.g. OrderRepository, PaymentGateway, Clock
    Command / query / result DTOs domain-api immutable records; validated on construction
    Domain events domain-api published through a driven port
    Entities, value objects domain-core never leak; mapped at the boundary
    Domain services (port impls) domain-core plain classes, constructor-injected ports
    Domain errors domain-api part of the contract — adapters must map them

    Testing

    • domain-core: plain JUnit against the driving ports, driven ports faked in-memory. This is where the bulk of the service's tests live, and they run in milliseconds.
    • domain-api: nothing to test beyond invariants encoded in command constructors. Deliberately no contract-test kit binding infrastructure implementations to the ports (2026-08-09 ruling): adapters are integration-tested against their real technology on their own terms (see infrastructure layer); the in-memory fakes encode only what the domain relies on, and drift between a fake and a real adapter is handled when observed, not with standing machinery.
