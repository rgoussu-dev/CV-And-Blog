    Application layer — primary adapters as deployment units

    # Per user-side adapter, an implementation module plus an API module where the contract is real — each mapping to a single unit of deployment — and the optional configurator that harbors the wiring.

    Conceptsaved 2026-08-09 #hexagonal-architecture#architecture#java#primary-adapters#deployment-unit

    Overview

    The application/ folder holds the primary (user-side) adapters: everything that drives the domain from the outside — REST endpoints, gRPC servers, Kafka consumers, cron jobs and the like. Each adapter has an implementation module, paired with an API module (DTOs + contracts) when its transport contract is real and consumable, and each maps to a single unit of deployment / container. An optional configurator module harbors the wiring of the domain and infrastructure modules so the adapters stay thin.

    Key points

    • A module pair where the contract is real. <adapter>-api carries the transport contract: request/response DTOs, the OpenAPI spec or generated interfaces for REST, the .proto files and generated stubs for gRPC, message schemas for Kafka. <adapter>-app carries the implementation: controllers/handlers/consumers, DTO ↔ command mapping, the main class, runtime configuration.
    • Why the split: the API module is publishable. A client team (or a sibling service) can depend on rest-public-api or the proto stubs without ever seeing the implementation; contract-first workflows (OpenAPI, protobuf) get a natural home for generated sources.
    • The pair is earned, not imposed. An adapter with no consumable contract — a cron runner, an internal batch — is a single -app module; an empty -api would be ceremony. The test: could another team meaningfully depend on the -api artifact? If not, don't create it.
    • One adapter = one deployment unit. A service may ship two REST units (e.g. public API and back-office), one gRPC server, one Kafka consumer group, one cron runner — five containers, five <adapter>-app modules, each with its Dockerfile beside it. Scaling, resource profiles and rollout cadence are decided per adapter, not per service.
    • Adapters translate, never decide. An -app module maps transport DTOs to domain commands, dispatches them through the Mediator driving port from domain-api (the settled dispatch seam — see the domain layer), and maps results back. Business rules living in a controller are a smell — push them through the port.
    • The configurator is optional and is the only assembly point. It exposes the wiring of domain-core with the infrastructure modules (as Spring @Configuration / CDI producers); each deployment unit imports it and selects what it needs. Without one, each *-app does its own wiring — acceptable while there is one deployment unit, repetitive beyond that.
    • No adapter depends on another adapter. Cross-adapter reuse happens in the domain, or not at all.

    Details

    Anatomy of one adapter pair

    application/rest-public/
├── rest-public-api/
│   ├── pom.xml                        # no domain deps; transport contract only
│   └── src/main/java/…/api/
│       ├── OrderRequest.java          # DTOs — transport-shaped, not domain-shaped
│       ├── OrderResponse.java
│       └── openapi.yaml               # or generated interfaces from it
└── rest-public-app/
    ├── pom.xml                        # depends on: rest-public-api, domain-api, configurator
    ├── Dockerfile                     # the deployment unit's container definition
    ├── README.md                      # how to run THIS unit
    ├── AGENTS.md                      # conventions for THIS unit
    └── src/main/java/…/
        ├── RestPublicApplication.java # main class
        ├── OrderController.java       # calls driving ports from domain-api
        └── OrderApiMapper.java        # DTO ↔ command/result mapping

    The same shape repeats wherever a contract exists — for grpc-server the -api module holds .proto + generated stubs; for kafka-consumers it holds the message schemas (Avro/JSON schema) the topics carry. For cron-jobs there is no consumable contract, so it stays a lone cron-jobs-app module — the tree stays predictable because the rule is uniform (pair ⇔ real contract), not because every adapter carries two modules.

    The configurator

    • Lives at application/configurator; depends on domain-api, domain-core, and the infrastructure modules; is depended on by the *-app modules. It is the one place allowed to see both sides of the hexagon.
    • Keep it declarative: bean/producer definitions binding each driven port to a chosen adapter, transaction decoration, nothing else. If logic accumulates there, it belongs in the domain.
    • When deployment units need different subsets of infrastructure, split the wiring into per-concern configuration classes (persistence, messaging, clients) so a unit imports only what it uses — the Kafka consumer unit shouldn't drag the Postgres wiring (and driver) into its image.
