    Infrastructure layer — secondary adapters & the granularity debate

    # Folder or single module — infrastructure granularity is decided ad-hoc per context; the forcing question is which deployment units need which driven adapters, with a commons module harboring the ubiquitous ports.

    Conceptsaved 2026-08-09 #hexagonal-architecture#architecture#java#secondary-adapters#infrastructure

    Overview

    The infrastructure layer holds the secondary (driven) adapters: implementations of the driven ports declared in domain-api — persistence, messaging producers, external API clients, clocks. Its shape is deliberately not fixed by the reference: granularity is decided ad-hoc, per context — a single module or several more granular ones, depending on the granularity required, since some secondary ports may not be needed by every deployment unit. This note records the forces on that decision and the shapes to choose between (settled in the 2026-08-09 discussion).

    Key points

    • The forcing fact: deployment units need different subsets of the driven adapters. A Kafka-consumer unit that only writes to Postgres shouldn't ship the billing HTTP client; a read-only REST unit shouldn't ship the Kafka producer. Whatever shape is chosen must let each unit's dependency list say exactly what it touches.
    • Granularity is the trade-off itself — decide it ad-hoc. Both shapes are legitimate: a single module where the service is small or its deployment units homogeneous; several granular modules — one per (port × technology), e.g. persistence-postgres, messaging-kafka, client-billing — the day deployment units need different subsets. The reference refuses a fixed rule; the forcing question is always which units need which adapters.
    • Ubiquitous ports live together in a commons module. Secondary ports used throughout with no operational footprint of their own — clock, id generation and the like — are harbored in a single common module (infrastructure/commons) rather than one micro-module each or configurator-supplied defaults.
    • Infra modules depend on domain-api and their own technology — nothing else. Never on domain-core, never on each other. The commons module is an infra module like any other (it implements ports); shared plumbing between adapters (a common error mapper, shared testcontainers setup) is a different thing and remains a warning sign, not a convenience.
    • Each module ships its own configuration (Spring @Configuration / auto-configuration, CDI producers) so the configurator merely selects modules rather than knowing their internals.
    • No contract testing between infra and the domain contract. Each module is integration-tested against its real technology (Testcontainers) on its own terms; the domain is tested against its in-memory fakes. The known risk — a fake drifting from real adapter behavior — is accepted and handled when observed, not with a standing contract-test kit.

    Details

    The three candidate shapes

    Shape Pros Cons Verdict
    Single infrastructure module trivial build, no ceremony every unit drags every driver: fat images, wide attack surface, muddy test scope, slow builds legitimate while the service is small or its units homogeneous
    Folder, one module per adapter units cherry-pick; per-adapter tests & deps; tech swap is localized more POMs, more ceremony legitimate the day units need different subsets
    Per-deployment-unit infra modules each unit fully self-describing duplicates adapters shared by several units — same Postgres mapping code twice rejected; the pick-list belongs in the unit's POM, not in copied code

    The first two are a context call, not a progression with a "right" end state — that ad-hoc judgement is the design decision this layer asks of you. The third is out regardless.

    Granularity heuristics (when going granular)

    • Split per (driven port × technology) pair, not per port alone: OrderRepository on Postgres is persistence-postgres; if an alternative DynamoDB implementation exists, that's persistence-dynamodb, not a second package in the same module — the point is that a deployment unit's POM names its technologies.
    • One module may implement several small ports of the same technology — the Postgres module can implement OrderRepository and CustomerRepository; splitting those would be ceremony without a consumer that wants one and not the other. Split when a real deployment unit wants the subset.
    • The module name states the technology, the package inside states the port. Reading a deployment unit's dependency list should read like its ops runbook: postgres, kafka, billing API.

    Settled (2026-08-09 discussion)

    • Ambient ports (Clock, id generation): a commons module harboring the common secondary ports used throughout — not per-port micro-modules, not configurator-supplied defaults.
    • Contract testing between infra and the domain contract: ruled out. Infra modules are integration-tested against their real technology on their own terms; the domain owns its fakes. No contract-test kit, so the question of where one would live is moot.
