    JVM implementations compared

    # The JVM specification versus its implementations — HotSpot, OpenJ9, GraalVM, Azul — and the OpenJDK distribution landscape.

    Conceptsaved 2026-08-09 #java#jvm#gc#jit#runtimes

    Overview

    "The JVM" is three distinct things: a specification (the JVMS) defining what any conforming virtual machine must do, several implementations of it with very different engineering trade-offs, and dozens of distributions — vendor builds of the same OpenJDK source differing mostly in support terms and packaging. Knowing which layer a claim applies to ("Java is slow to start", "Java has pauseless GC") is the difference between cargo-culting and choosing a runtime deliberately.

    Key points

    • Spec vs implementation vs distribution: the JVMS fixes behaviour; HotSpot, OpenJ9, GraalVM and Azul Zing implement it differently; Temurin, Corretto, Zulu et al. build the same HotSpot-based OpenJDK source.
    • HotSpot: the OpenJDK reference implementation and default nearly everywhere — tiered JIT (C1/C2), the richest GC roster (G1, ZGC, Shenandoah, Parallel, Serial).
    • OpenJ9 (Eclipse, shipped as IBM Semeru): memory footprint and fast start via class sharing and a different JIT/AOT design; strong in constrained containers.
    • GraalVM replaces C2 with a JIT written in Java and adds Native Image AOT — see the deep dive.
    • Azul Zing (Platform Prime) sells pauseless GC (C4) and an LLVM-based JIT (Falcon) for latency-critical, large-heap workloads.
    • Conformance is tested, not assumed: an implementation may call itself Java only after passing the TCK/JCK compatibility suite.
    • Distribution choice is a support decision, not a performance one: same source, different build cadence, licensing, vendor backing.

    Details

    The JVM specification

    The Java Virtual Machine Specification (JVMS) is the contract every implementation signs up to: the class file format (constant pool, attributes), the bytecode instruction set and its semantics, the verification rules that make untrusted bytecode safe to load, classloading/linking, and the run-time data areas (heap, per-thread stacks, method area). Crucially, it also defines what it leaves open: GC algorithms, JIT strategy, object layout and thread scheduling are implementation detail — exactly the space where HotSpot, OpenJ9 and Zing diverge. Any language compiling to conforming class files (Kotlin, Scala, Clojure) rides on the same contract. Conformance is enforced by the Technology Compatibility Kit (TCK, historically JCK): passing it is what legally permits the "Java compatible" claim, and every serious distribution vendor runs it against each build. Saved reference: The JVMS.

    HotSpot

    HotSpot is the JVM inside OpenJDK and thus what almost every Java process runs. Execution is tiered: bytecode starts interpreted, hot methods are compiled by C1 (fast compiles, light optimization, inserts profiling), the hottest graduate to C2 (aggressive inlining, escape analysis, loop optimizations, deoptimization when speculative assumptions break). The GC roster is the broadest of any implementation:

    • G1 — the default; region-based, pause-target driven, good general balance.
    • ZGC — sub-millisecond pauses on multi-terabyte heaps, generational since 21.
    • Shenandoah — concurrent compacting collector with similar low-pause goals.
    • Parallel — maximum throughput when pauses don't matter (batch).
    • Serial — single-threaded; tiny heaps and single-CPU containers.
    • Epsilon — a no-op collector: allocates, never reclaims; for benchmarking allocation cost and short-lived, pre-sized workloads.

    OpenJ9

    Eclipse OpenJ9 (originally IBM J9, shipped with an OpenJDK class library as IBM Semeru) is a from-scratch implementation prioritizing memory footprint and start-up. Its signature feature is the shared classes cache: verified class metadata and AOT-compiled code shared across JVM processes via a memory-mapped cache, cutting both start time and per-process footprint. The JIT is its own — with an optional remote JITServer offloading compilation, useful in memory-capped containers — and AOT has been first-class far longer than in HotSpot. GC policies (gencon default, balanced, metronome) differ from HotSpot's roster. Sweet spot: dense container deployments where dozens of JVMs share a node.

    GraalVM

    GraalVM starts from HotSpot but swaps C2 for the Graal compiler, a JIT written in Java, and layers on the Truffle polyglot framework and — its main draw — Native Image AOT compilation to a standalone binary with near-instant start-up. The trade-offs (closed-world assumption, reachability metadata, peak-throughput and build-time costs) deserve their own note: GraalVM deep dive.

    Azul

    Azul ships two distinct things: Platform Core, a plain OpenJDK/HotSpot distribution (Zulu — see below), and Platform Prime (formerly Zing), a different runtime. Prime's C4 collector (Continuously Concurrent Compacting Collector) compacts fully concurrently — effectively pauseless GC on heaps into the hundreds of gigabytes — and Falcon, an LLVM-based JIT, replaces C2 for higher peak code quality; ReadyNow persists profiles to warm up fast after restart. Commercial, Linux-only; sweet spot is latency-sensitive trading and large-heap services where GC pauses dominate tail latency.

    Distributions

    All of these are the same HotSpot-based OpenJDK source, built, TCK-tested and supported by different vendors:

    • Eclipse Temurin (Adoptium) — the community default; broad platform coverage, no strings attached.
    • Amazon Corretto — Amazon's build, free LTS support, default on AWS services.
    • Azul Zulu — Azul's OpenJDK build (distinct from Prime); wide version/platform matrix, paid support available.
    • BellSoft Liberica — full/lite/native flavours, strong ARM/Alpine coverage; the JDK behind many Spring tooling defaults.
    • Microsoft Build of OpenJDK — Microsoft's build, default on Azure.
    • Oracle JDK — Oracle's binaries; NFTC makes an LTS free only until one year after the next LTS ships, then updates need a paid subscription. Oracle's GPL OpenJDK builds (jdk.java.net) get just six months of updates. Read the terms before production.

    Pick a distribution on support lifetime, platform coverage and procurement comfort — benchmarking Temurin against Corretto is measuring noise.
