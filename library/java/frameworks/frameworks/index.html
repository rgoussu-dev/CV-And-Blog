    Java application frameworks — the landscape

    # How Spring, Quarkus and Micronaut differ in DI approach, footprint, native-image story and standards adherence, and where Jakarta EE sits.

    Conceptsaved 2026-08-09 #java#frameworks#spring#quarkus#micronaut#jakarta-ee

    Overview

    Three frameworks dominate server-side Java today: Spring — the incumbent, an ecosystem so broad it is effectively the default; Quarkus — Red Hat's container-first stack that moves framework work (classpath scanning, reflection metadata, config parsing) from runtime to build time; and Micronaut — which goes furthest, doing dependency injection and AOP entirely at compile time with annotation processors, no reflection and no runtime proxies. Around them sit the Jakarta EE application servers (WildFly, Payara, Open Liberty) implementing the full spec platform, and lighter players: Helidon (Oracle, MicroProfile

    • its own Níma virtual-thread server), Vert.x (event-loop toolkit rather than framework — it also underpins Quarkus), and Dropwizard (a pre-Boot curated bundle of Jetty, Jersey and Jackson, historically important, now niche).

    Key points

    • Spring: runtime IoC container, huge ecosystem (Boot, Data, Security, Cloud); its own APIs rather than Jakarta specs, though it consumes JPA, Servlet and Bean Validation.
    • Quarkus: build-time augmentation; standards-first (Jakarta EE core profile + MicroProfile via SmallRye); best-in-class GraalVM native-image support and dev experience (live reload, Dev Services).
    • Micronaut: compile-time DI/AOP via annotation processing — fastest cold start on the JVM, natural GraalVM fit; own APIs on a JSR-330 lineage.
    • The trade-off axis: runtime flexibility & ecosystem breadth (Spring) vs. build-time processing for startup/memory/native (Quarkus, Micronaut).
    • Jakarta EE servers still matter in enterprises with existing EAR/WAR estates; MicroProfile is the microservice-oriented spec layer Quarkus and Helidon implement.
    • Choosing: existing team knowledge and library needs usually decide — all three are production-grade; footprint arguments only bite for serverless/high-density containers.

    Comparison

    Spring (Boot 3.x) Quarkus Micronaut
    DI approach Runtime: reflection, classpath scanning, dynamic proxies (AOT option since Boot 3) Build-time: ArC pre-computes the CDI bean graph during augmentation Compile-time: annotation processors generate bean definitions; zero reflection
    Startup / memory Heaviest on JVM; much improved with CDS/AOT Fast JVM start, low RSS; "supersonic" in native Fastest JVM cold start of the three; low memory
    Native image Supported (GraalVM AOT, native-maven-plugin), more friction with dynamic libraries First-class, default workflow (Mandrel distribution) First-class by design — no reflection to configure
    Ecosystem breadth Enormous — the reference integration surface Large and growing (extensions catalog) Solid but smallest of the three
    Standards adherence Own APIs; consumes Jakarta specs (JPA, Servlet, Validation) Implements Jakarta EE core profile + MicroProfile Own APIs, JSR-330 annotations; optional Jakarta bridges
    Sweet spot Broad enterprise services, anything needing an integration nobody else has Kubernetes/serverless, standards-minded teams, native binaries Microservices, CLI tools, AWS Lambda, low-footprint fleets
