    Concurrency and Parallelism

    # Core concepts governing how programs execute multiple tasks simultaneously, and the trade-offs between competing approaches.

    Conceptsaved 2026-07-26updated 2026-08-09 #concurrency#parallelism#threading#async#system-design

    Overview

    Concurrency is the ability of a program to deal with multiple tasks at once (interleaving or overlapping their execution); parallelism is the ability to execute multiple tasks at the same time on multiple cores. The two are related but distinct: a concurrent program is not necessarily parallel, and a parallel one is not necessarily concurrent in the classic sense. Getting this right is one of the enduring crossroads in software engineering — the choice of model (threads, async, actors, STM, channels…) shapes correctness, performance, and maintainability.

    Key points

    • Concurrency ≠ Parallelism: concurrency is a design property (structure); parallelism is a runtime property (execution on multiple cores).
    • Shared state is the root of most bugs: race conditions, deadlocks, and livelocks arise from uncoordinated access to mutable shared memory.
    • Models differ in trade-off: threads (OS) vs. green threads / fibres vs. async/await (cooperative) vs. actors (message-passing, no shared state) vs. STM (optimistic transactions).
    • Lock granularity matters: coarse locks are safe but slow; fine-grained locks are fast but complex and error-prone.
    • Amdahl's Law: the speedup from parallelism is bounded by the serial fraction of the work — most programs hit this ceiling sooner than expected.
    • Platform matters: the JVM (virtual threads in Java 21+), Go (goroutines + CSP), Rust (fearless concurrency via ownership), and the OS model each impose their own primitives and costs.

    Practice

    • Dining philosophers (source) — implement it three ways (lock ordering, arbitrator, try-lock with backoff) — and make it deadlock on purpose first, so you recognize the symptom.
    • Worker pool (source) — bounded queue, N workers, graceful shutdown; build it in Java, Go, and Rust and feel three models' costs for the same design.
    • One Billion Row Challenge (source) — parallelize a real aggregation and watch Amdahl's law and contention — not the core count — decide the speedup.
    • Build your own Redis (source) — choose the concurrency model for a real server (event loop vs. thread-per-connection) and live with the consequences under concurrent clients.
