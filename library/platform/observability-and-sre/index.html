    Observability & SRE practice

    # Metrics, logs, and traces; SLOs and error budgets; incident response — running systems as an engineering discipline.

    Conceptsaved 2026-08-08 #observability#sre#monitoring#operations#reliability

    Overview

    Observability is the ability to ask new questions of a running system without shipping new code; SRE (Google's Site Reliability Engineering) is the discipline that turns "keep it up" into engineering — reliability targets as numbers, alerting on user pain, and incidents as learning material. It is the operational half of every architecture decision: a microservice estate without this is a distributed system you can't see.

    Key points

    • Three signals, one goal: metrics (cheap, aggregable — Prometheus model, RED/USE methods), logs (structured, correlated — not grep-able prose), traces (per-request causality across services — OpenTelemetry as the now-standard instrumentation layer). Correlation IDs tie them together.
    • SLI → SLO → error budget: measure what users experience (latency p99, availability, correctness), set a target, and spend the remaining unreliability deliberately — the error budget is the contract that arbitrates "ship features" vs. "improve reliability".
    • Alert on symptoms, not causes: page only for user-impacting, actionable conditions; everything else is a dashboard or a ticket. Alert fatigue is a reliability risk in itself.
    • Incident response: roles (incident commander, comms), severity levels, and the blameless postmortem — the failure is systemic until proven otherwise; action items tracked like features.
    • Cardinality is the cost model: high-cardinality labels (user IDs in metric labels) are what blow up observability bills; traces + exemplars handle the per-request questions instead.
    • Toil budget: SRE caps manual repetitive work and automates it away — the practice that separates SRE from traditional ops.
    • To explore: continuous profiling as the fourth signal, chaos engineering, on-call health, OpenTelemetry semantic conventions.

    Practice

    • SadServers (source) — timed "why is this server sad?" troubleshooting scenarios on real broken machines; teaches diagnosis under pressure, the raw skill incident response runs on.
    • RED dashboard for your own service (source) — instrument a side project with Prometheus metrics, build a rate/errors/duration dashboard in Grafana, and add one symptom-based alert; teaches the metrics signal and alerting on user pain, not causes.
    • OpenTelemetry demo, then break it (source) — run the OTel demo shop, follow one request across services via traces, then inject a failure with its feature flags and find it from telemetry alone; teaches trace-first debugging and correlation across the three signals.
    • Write real SLOs (source) — pick a service you run (even a hobby one), define SLIs from what users experience, set SLO targets, and compute the error budget; teaches that the hard part is choosing what to measure, not the arithmetic.
    • Blameless postmortem drill (source) — write a full postmortem for a real past failure (yours or a public one): timeline, contributing factors, action items tracked like features; teaches incidents-as-learning-material by producing the artifact.
