    Storage access from Rust — the map

    # How Rust reaches every storage kind — no stdlib layer, per-store drivers, the sqlx/diesel/sea-orm spectrum for relational — mapped store by store.

    Conceptsaved 2026-08-09 #rust#storage#databases#drivers#sqlx

    Overview

    Rust's storage story is even flatter than Go's: there is no database/sql, no JDBC — no stdlib abstraction of any kind. Every store is reached by a community or vendor crate speaking the wire protocol, and the layering decisions (pooling, mapping, query building) are made per store. The relational corner is where the ecosystem's signature idea lives: sqlx checks your SQL against the real database at compile time — a third position neither the JVM (runtime ORMs) nor Go (runtime database/sql

    • sqlc's offline codegen) occupies in quite the same way.

    Key points

    • No common abstraction — and no ORM culture: the relational spectrum runs tokio-postgres (raw) → sqlx (checked SQL) → sea-orm (async ORM) → diesel (DSL, compile-checked, sync-first); most teams stop at sqlx. SQL-in-the-open is the house aesthetic, same as Go's.
    • Pooling is explicit and per-crate: sqlx ships its own pool; raw drivers pair with deadpool or bb8; every non-relational client manages its own — the slot HikariCP fills once for the whole JVM is filled per store here.
    • Async by default, with cancellation semantics: every call is .await on Tokio, and dropping a future cancels the operation — the moral equivalent of Go's contexts, but implicit in the model; timeouts are tokio::time::timeout wrappers or pool/driver options.
    • Transactions are values with lifetimes: pool.begin().await? → Transaction<'_> passed explicitly; commit is a method, drop means rollback — the RAII twist on Go's explicit *sql.Tx, and the compiler prevents using a connection across a transaction's lifetime wrongly.
    • Mapping is derive-based everywhere: #[derive(sqlx::FromRow)], serde for document stores, scylla's row derives — struct tags in Go, annotations in Java, derives here.
    • Testing is the same Testcontainers-shaped story: testcontainers-rs and #[sqlx::test] against real engines.
    • Rust is increasingly the implementation language of storage: ScyllaDB's shard-aware driver, SurrealDB, GreptimeDB, Qdrant, sled/redb embedded stores — which is why some of the client crates below are vendor-first-class.

    Choosing an entry point

    • Connectivity, pool exhaustion, timeouts → the driver/pool layer; nothing above it hides the problem.
    • Query-heavy relational work → settle the sqlx vs sea-orm vs diesel question early; it shapes the whole repository layer — the criteria live in the relational deep dive.
    • The handler layer calling all of this is the web-framework question, and barely interacts with the storage choice — same separation as in Go.
