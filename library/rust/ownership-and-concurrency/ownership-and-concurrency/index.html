    Ownership, memory & concurrency — the model

    # The map of Rust's core model — how one compile-time mechanism, ownership, answers both the memory-management question and the memory-model question, and how the group's notes fit together.

    Conceptsaved 2026-08-09 #rust#ownership#memory#concurrency#internals

    Overview

    Java's memory & GC group opens by splitting "memory" into two contracts: management (where bytes live, when they're reclaimed) and the model (what one thread observes of another's writes). Rust's defining move is answering both contracts with one compile-time mechanism. Ownership decides when every value is freed — deterministically, at scope exit, no collector — and the same aliasing rules, lifted to thread boundaries by Send/Sync, make data races a compile error. This group takes the deep dive's core-model bullets to full depth: the borrow checker as a working tool, not a hazing ritual.

    Key points

    • One mechanism, two payoffs: aliasing XOR mutation (&T many, &mut T one) is simultaneously the memory-safety rule (no use-after-free through a stale alias) and the data-race rule (no unsynchronized concurrent writes) — the insight the whole language is built around.
    • Management is resolved statically: every value has one owner; drop runs at the owner's scope exit (RAII). There is no runtime deciding when to free — the compiler is the garbage collector, and its output is ordinary frees compiled into the binary.
    • The model is enforced statically too: Send/Sync are auto-derived marker traits the compiler checks at every spawn; the atomics' ordering vocabulary (the C++11 model, cousin of Java's JMM) only becomes your problem when you opt into unsafe or raw atomics.
    • The cost is paid at the API: what GC'd languages resolve at runtime, Rust makes you design for — lifetimes in signatures, Arc vs &, restructure-vs-clone decisions. The learning curve of this group is the language's actual learning curve.
    • The reading order: ownership & borrowing (the rules and the fights) → lifetimes (naming how long borrows live) → memory without GC (layout, smart pointers, interior mutability) → fearless concurrency (threads, channels, atomics — the rules crossing thread boundaries).
    • The spine is the Book: chapters 4, 10.3, 15 and 16 of The Rust Programming Language map one-to-one onto this group's notes; the Rustonomicon is the unsafe-Rust sequel where the guarantees come from and how not to break them.
    • Escape hatches are part of the model, not exceptions to it: interior mutability moves the aliasing check to runtime (RefCell) or to a lock (Mutex); unsafe narrows the trust boundary to audited blocks — and miri checks those blocks against the same rules dynamically.
