    The Rust build ecosystem

    # Cargo as the one build path — crates.io as the single registry, the artifact formats from bin to cdylib to WASM, and where Bazel-scale exceptions appear.

    Conceptsaved 2026-08-09 #rust#build#cargo#packaging#crates-io

    Overview

    Where Java offers three build tiers (bare JDK tools, Maven, Gradle) and Go ships one first-party path, Rust is at the Go end and further: cargo is the build system, the package manager, the test runner and the publishing tool, and crates.io is the single registry the whole ecosystem publishes to. There is no build-tool debate and no competing registry; "how do I build this?" has had one answer since 2015. The interesting structure is below cargo: what artifacts a crate can produce (and why the lack of a stable ABI shapes that list), and the release-engineering layer that grew alongside.

    Key points

    • One tool, one registry: cargo build/test/publish against crates.io — no Maven-vs-Gradle choice, no proxy/VCS indirection like Go's module system; crates.io hosts the actual source archives, immutably (yank hides, never deletes).
    • The project model — workspaces, features, profiles, build.rs, lockfile semantics, publishing — is deep enough for its own note: Cargo in depth.
    • Default artifact is a static native binary: like Go, deployment is "copy the file"; unlike Go, there's no runtime inside it — see the format table below.
    • No stable ABI is the shaping constraint: Rust-to-Rust dynamic linking (dylib, rlib reuse) only works within one exact compiler version, so the ecosystem compiles from source, every time, per toolchain — the deep reason builds are slow and sccache exists. Stable interop across a shared-library boundary means the C ABI (cdylib/staticlib) — or extern "C" shims, with abi_stable/stabby as community workarounds.
    • Release engineering — cross-compilation, cross, cargo-dist, and the supply-chain toolbox (cargo-audit/deny/vet) — has its own note: Building & releasing.
    • Monorepo-scale exceptions: Bazel (rules_rust) and Buck2 (itself written in Rust) appear where hermetic multi-language builds pay their complexity — they wrap rustc and often still consume cargo metadata; nobody replaces cargo for dependency semantics.
    • Task runners orchestrate, never build: just (the community favourite), cargo-make, plain Make — thin glue over cargo invocations, same posture as Go.

    Details

    Artifact formats — the crate-type table

    crate-type Produces Consumed by Notes
    bin Native executable OS directly Static by default (musl for fully-static Linux); the deployment norm
    lib / rlib Rust static library + metadata Other Rust crates, same compiler only The default library form; what cargo build makes of every dependency
    dylib Rust dynamic library Other Rust code, same compiler only Unstable ABI — rarely what you want; mainly compiler-internal use cases
    cdylib C-ABI shared library (.so/.dylib/.dll) Any language via FFI; WASM The FFI export format — Python extensions (PyO3), Node addons, plugins
    staticlib C-ABI static archive (.a/.lib) C/C++ link steps Embedding Rust into existing native builds
    proc-macro Compiler plugin rustc at compile time Runs in the compiler; the serde/tokio-macros mechanism
    WASM module --target wasm32-* (bin or cdylib) Browsers (wasm-bindgen), WASI runtimes Tens of KB — no runtime to carry; see compilers & the language definition
    Container image Multi-stage Dockerfile, FROM scratch/distroless Registries Same near-empty-base story as Go; cargo-chef layers dependency builds for cache reuse

    The registry, one paragraph

    crates.io enforces semver-shaped versions, immutable uploads and a flat global namespace (no user prefixes — name squatting is a real drawback the JVM's reverse-domain groupIds avoid). The index is served over a sparse HTTP protocol; private registries (Artifactory, Kellnr, Shipyard) and git/path dependencies cover the non-public cases.
