    Testing in Rust — strategies & tooling map

    # Map of Rust testing strategies — unit to security — built on the built-in test harness and cargo-nextest, with the tools per strategy and links to the deep-dive notes.

    Conceptsaved 2026-08-09 #rust#testing#tooling#quality

    Overview

    Rust ships its testing substrate with the language, Go-style: #[test] functions run by the built-in libtest harness under cargo test, three test kinds by convention (unit tests in-module, integration tests in tests/, doctests in the docs), and no framework to choose. The community layer on top is unusually strong on the correctness-hardening end — property-based testing, fuzzing, mutation testing, miri — because the language attracts code where being right matters. This note maps the strategy axes onto the tools worth knowing and hands off to a deep-dive per strategy.

    Key points

    • The built-in harness is the substrate: #[test], #[should_panic], assert! macros, Result-returning tests — everything below plugs into it and runs under cargo test (or, in practice, cargo-nextest).
    • Three test locations with meaning: unit tests in a #[cfg(test)] mod tests beside the code (private access), integration tests in tests/ (compiled as external consumers — public API only), doctests in /// examples (never-stale documentation).
    • The type system moves the pyramid's floor: whole test categories other ecosystems need (null checks, type confusion, data-race repros) are compile errors — suites skew toward behaviour, properties and integration rather than defensive checks.
    • House position — integration is mid-priced: no httptest-style stdlib, but a tower Router drives in-process via oneshot, and testcontainers/sqlx-test make real-database tests routine — flatter pyramid than Java, steeper than Go.
    • Assertions are stdlib-first: assert_eq! + pretty_assertions for diffs; insta for snapshots; no AssertJ-style fluent culture.
    • Coverage via cargo llvm-cov; it says what ran — mutation testing with cargo-mutants says what was asserted.
    • Generated inputs are a first-class habit: proptest for invariants, cargo-fuzz for hostile bytes — the two complement, and shared corpus/regression files are the norm — see Property-based testing & fuzzing.
    • Performance and security are testing concerns: criterion/divan benchmarks and cargo-audit/miri belong in the same CI portfolio.

    Details

    Strategy → tools → deep dive

    Strategy What it verifies Standard Rust tools Deep dive
    Unit One behaviour in isolation, milliseconds built-in harness, pretty_assertions, insta, mockall, rstest Unit testing
    Integration Code + real dependencies (DB, broker, HTTP) tests/, tower oneshot, testcontainers-rs, #[sqlx::test], wiremock Integration testing
    End-to-end The deployed system through its public surface reqwest smoke suites, thirtyfour/playwright (browser), contract tests End-to-end testing
    Mutation Quality of the test suite itself cargo-mutants Mutation testing
    Property-based & fuzzing Invariants over generated inputs; crashes on hostile input proptest (quickcheck legacy), cargo-fuzz (libFuzzer), AFL, arbitrary Property-based testing & fuzzing
    Performance Latency/throughput of code and system criterion, divan, iai-callgrind (micro); goose, k6 (load) Performance & load testing
    Security Known vulns, unsafe soundness, supply chain cargo-audit/deny/vet, cargo-geiger, miri, fuzzing Security testing

    Choosing the boundary

    • Pure domain logic → unit tests beside the code; reach for proptest the moment a function has an invariant ("parse ∘ print = id").
    • Handlers and middleware → in-process router tests (oneshot); a real socket only for the smoke layer.
    • Persistence/messaging glue → testcontainers-rs or #[sqlx::test] against the real engine; compile-time-checked queries already killed a class of these tests.
    • Anything unsafe → miri in CI, fuzz targets on the parsing/FFI surface.
    • Suite trustworthiness → cargo-mutants on the crates where correctness pays rent.
