    Hexagonal architecture reference implementation — Rust

    # The house hexagonal reference realized for Rust — a Cargo workspace with crates as compile-enforced walls, traits as ports, binary crates as deployment units, and dyn-by-default wiring with generics as the measured escape hatch.

    Conceptsaved 2026-08-09 #hexagonal-architecture#architecture#rust#cargo#workspace#reference-implementation

    Overview

    The house reference implementation of hexagonal architecture for Rust, standing on its own terms. The shared principles live in that note — trisection, one deployment unit per primary adapter, a contract face and an implementation face for the domain, containerisation beside its unit, per-crate README.md/AGENTS.md. Rust's realization is a Cargo workspace whose crate graph is the architecture: crates are real compilation units with an enforced dependency graph, so every boundary rule is held by the compiler, no linter needed. The decision the language itself forces is how ports are wired: trait objects vs generics — settled below (2026-08-09 discussion).

    Key points

    • The workspace is the backbone. The root Cargo.toml declares members and centralises versions via [workspace.dependencies]; cargo build -p rest-public-app builds exactly one deployment unit.
    • Ports are traits; the domain is two crates: domain-api (traits for driving and driven ports, command/result types, domain events — zero dependencies) and domain-core (entities, services implementing driving ports — depends only on domain-api). The crate graph makes infra → domain-core a compile error — the dependency rule, enforced by rustc.
    • One binary crate per primary adapter under application/, each a deployment unit with its Dockerfile beside it. The *-api/*-app pair exists where the contract is real (proto crate for gRPC, generated OpenAPI types crate for REST); cron-style units are a single binary crate — the pair is earned by a consumable contract, never imposed for symmetry.
    • Infrastructure granularity is decided ad-hoc per context — a single crate or one per (port × technology) (persistence-postgres, messaging-kafka, client-billing), the forcing question being which deployment units need which driven adapters; ubiquitous ports (clock, id generation) sit together in a commons crate. Cargo features gate variants of one adapter, never adapter selection — the unit's [dependencies] does that.
    • The wiring rule — Arc<dyn Port> at the seams by default, generics as the measured escape hatch. Trait objects give late binding and a readable main.rs; the cost is that async trait methods aren't natively object-safe, so dyn ports mean boxed futures — one heap allocation per port call. Generics (PlaceOrderService<R: OrderRepository>) are zero-cost but monomorphize the assembly into type Tetris that infects every signature upward. The ruling: dyn is the default; generics are legitimate on hot paths, for measured performance reasons — a profiled boundary, not a style preference — and the crate that opts in keeps the generic parameters from leaking past its own public surface where possible.
    • Port design follows from the ruling: ports in domain-api are object-safe (no generic methods), Send + Sync, boxed-async accepted — so every port can be wired as dyn, and a generics opt-in remains possible per call site.
    • Async is decided at the edges: the runtime (tokio) is a dependency of binary crates and infra crates; domain-api traits stay runtime-agnostic (async fn in traits / #[trait_variant], no tokio types in signatures) so the domain never depends on an executor.

    Details

    The derived workspace

    acme-service/
├── README.md / AGENTS.md
├── Cargo.toml                     # [workspace] members + workspace.dependencies
├── application/
│   ├── rest-public/
│   │   ├── rest-public-api/       # generated/shared transport types (lib crate)
│   │   └── rest-public-app/       # axum handlers, mapping, main.rs (bin crate)
│   │       └── Dockerfile
│   ├── grpc-server/               # tonic; -api crate holds proto + prost output
│   ├── kafka-consumers/
│   └── cron-jobs/                 # single bin crate; no -api needed
├── domain/
│   ├── domain-api/                # port traits, commands, events — no deps
│   └── domain-core/               # entities, services — depends on domain-api only
├── infrastructure/
│   ├── commons/                   # ubiquitous ports: clock, id generation
│   ├── persistence-postgres/      # sqlx; implements repository traits
│   ├── messaging-kafka/
│   └── client-billing/
├── compose.yaml
└── deployment/                    # IaC: OpenTofu modules + per-environment stacks

    No configurator crate: main.rs per binary is the assembly point. If several binaries wire identical subsets, extract a small lib crate of assembly constructors; that is a deduplication move, not a layer of the architecture.

    The layout elements and their enforcement

    Element Realization Held by
    the dependency rule the workspace crate graph rustc — a wrong edge is a compile error
    domain contract vs implementation domain-api / domain-core crates crate dependencies
    ports object-safe traits, Send + Sync, boxed-async accepted the house port-design rule
    adapter contract lib + bin crate pair where the contract is real; lone bin otherwise convention
    infra granularity per-context: single crate or one per (port × technology); commons for ubiquitous ports the unit's [dependencies]
    assembly point main.rs per binary convention
    wiring explicit construction, Arc<dyn Port> by default; generics on measured hot paths house rule
    supply-chain hygiene cargo-deny for licences and duplicates CI

    Nothing left open

    The compile-time cost of many small crates is settled (2026-08-09): accepted by design — the dependency-rule enforcement the crate separation buys is the point of the layout; the build cost is its price, not a factor to optimize the architecture around. (Port object-safety and the Send + Sync contract bounds were settled earlier by the wiring rule in Key points.)

    Examples

    Workspace root:

    [workspace]
resolver = "2"
members = [
  "domain/domain-api", "domain/domain-core",
  "infrastructure/persistence-postgres", "infrastructure/messaging-kafka",
  "application/rest-public/rest-public-api", "application/rest-public/rest-public-app",
]

[workspace.dependencies]          # versions declared once, like a parent POM
tokio = { version = "1", features = ["rt-multi-thread"] }
sqlx = { version = "0.8", features = ["postgres", "runtime-tokio"] }

    A port and its wiring:

    // domain-api
pub trait OrderRepository: Send + Sync {
    async fn save(&self, order: NewOrder) -> Result<OrderId, RepositoryError>;
}

// rest-public-app / main.rs — the configurator
let repo: Arc<dyn OrderRepository> = Arc::new(PgOrderRepository::new(pool));
let place_order = PlaceOrderService::new(repo.clone());
let app = rest_public::router(Arc::new(place_order));
