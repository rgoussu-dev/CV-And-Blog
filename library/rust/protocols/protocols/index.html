    Backend protocols in Rust — the map

    # How REST, GraphQL, gRPC, WebSockets/SSE and messaging map onto the de-facto crates — axum/reqwest, async-graphql, tonic, tokio-tungstenite, rdkafka/lapin/async-nats.

    Conceptsaved 2026-08-09 #rust#protocols#frameworks#api-design

    Overview

    Rust's protocol story is Go's taken one step further: not even HTTP lives in the standard library — every protocol is a crate, and for each there is one de-facto choice plus a short tail. What Rust adds over Go's map is a shared substrate beneath the crates: serde for every serialization boundary, Tokio for every I/O path, and tower's Service reaching across protocols — the same middleware stack can wrap a REST router and a gRPC server, which neither neighbour ecosystem manages. Contracts follow the same logic as everywhere: REST documents after the fact (utoipa), GraphQL and gRPC are schema-first by construction — the doc tooling per framework has its own note: API documentation in Rust.

    Key points

    • No stdlib networking above TCP: std::net stops at sockets; HTTP itself is hyper — the "de-facto crate per protocol" rule starts one layer lower than in Go.
    • serde is the universal codec layer: one #[derive(Serialize, Deserialize)] serves JSON (serde_json), and the same types often feed GraphQL and message payloads — the single most load-bearing crate in the ecosystem.
    • Codegen over reflection, by necessity: no runtime reflection exists, so every schema-first protocol compiles its contract into types — prost for .proto, async-graphql derives for SDL, utoipa derives for OpenAPI. Contract drift is a compile error more often than a runtime surprise.
    • Sync vs async, text vs binary — the axes are unchanged from the Java and Go maps; Tokio makes the long-lived-connection cases (streams, sockets, consumers) cheap the way goroutines do.
    • The client side is reqwest: the de-facto HTTP client (hyper + rustls, pools, middleware via reqwest-middleware) — named here once instead of per row.
    • Each deep dive names the concrete crates — that mapping is the point of this group.

    Details

    The protocol × crate matrix

    Protocol De-facto crates Notable alternatives Deep dive
    REST / HTTP APIs axum or actix-web + serde_json; reqwest (client); utoipa (OpenAPI) poem (OpenAPI-native), warp; progenitor (spec-first client) REST
    GraphQL async-graphql (+ axum/actix integrations) juniper; cynic / graphql-client (clients) GraphQL
    gRPC tonic + prost, tonic-build/buf grpc(-io) bindings, connect-style via tonic ecosystem gRPC
    WebSockets / SSE tokio-tungstenite; axum's WebSocketUpgrade & Sse actix-ws, fastwebsockets WebSockets & SSE
    Messaging (Kafka / AMQP / NATS) rdkafka (Kafka), lapin (RabbitMQ), async-nats (NATS) rskafka (pure Rust), amqprs Messaging

    Choosing

    The decision tree matches the neighbours': REST for public/browser-facing APIs, GraphQL when clients need flexible aggregation, gRPC for internal service-to-service (where tonic's tower interop makes it feel native rather than bolted on), WebSockets/SSE when the server pushes, messaging when the work can be asynchronous. Rust-specific nudge: the gRPC and Kafka paths are unusually strong here — tonic and rdkafka are production-proven where some Rust corners are still maturing — while GraphQL sees less production use than in the JVM world.
