    Security in Rust applications — the map

    # How the recurring security concerns map onto Rust's crates — composed as tower middleware and typed APIs, with memory safety covering some fronts and none of the others.

    Conceptsaved 2026-08-09 #rust#security#frameworks#middleware

    Overview

    Rust's application-security posture is Go's taken further in both directions. Like Go, there is no Spring Security — each concern is a small, well-known crate composed as middleware (here: tower layers) — and nothing is on by default. Unlike Go, there is no curated crypto stdlib either: everything is a crate, chosen from an unusually high-quality shelf (rustls, RustCrypto). And one concern class is simply absent: memory-corruption vulnerabilities are gone from safe code — which matters, and which attackers route around by aiming at logic, injection and dependencies like everywhere else. This note is the concern → crate map; the theory lives in the Security theme, the contrast in Security in Java applications.

    Key points

    • What memory safety buys — and doesn't: buffer overflows, use-after-free and data races are compile errors in safe Rust; injection, authz mistakes, SSRF, weak crypto choices and supply-chain compromise are untouched — the deep treatment is in Web security in Rust apps.
    • Authn is a middleware + extractor affair: token validation as a tower layer or an axum FromRequestParts extractor (an AuthenticatedUser argument = an authenticated route, checked by the compiler) — the typed twist on Go's wrapper functions.
    • OAuth2/OIDC is the perimeter: the oauth2 crate for flows, openidconnect for OIDC discovery/validation, jsonwebtoken for JWT verification — see OAuth2 & OIDC in Rust.
    • Authorisation: in-handler checks by default; casbin-rs for policy models, oso (embedded Polar) while it lasted, OPA via HTTP — same externalisation options as Go, none dominant.
    • The web attack surface is handled piecemeal: sqlx parameterization, askama/maud auto-escaping, tower-http CORS/limits, tower-sessions — Web security walks the OWASP list.
    • Crypto is crate-first and excellent: rustls for TLS, ring vs the RustCrypto families for primitives, zeroize/secrecy for secret hygiene — see Cryptography in Rust.
    • Secrets come from the environment or vault/KMS crates (vaultrs, aws-sdk-kms) — nothing in-language; secrecy::SecretString keeps them out of Debug output.
    • Supply chain is the Rust-specific risk concentration: deep dependency trees + build.rs/proc-macro build-time execution — cargo-audit/deny/vet are part of the security posture here, not just hygiene; see Security testing.
    • No framework defaults means the checklist is yours: same as Go — a shared internal tower stack (auth, headers, limits, tracing) substitutes for what Spring auto-configures.

    Rust as security infrastructure

    The asymmetry noted for Go holds here with different genres: while Rust applications assemble security from crates, Rust is becoming the implementation language of security-critical infrastructure — TLS stacks (rustls displacing OpenSSL in curl/Apache experiments), sudo-rs and the coreutils rewrites, the Signal and WireGuard ecosystems' components, HSM/PKI tooling, and memory-safe rewrites funded explicitly as security work (ISRG's Prossimo). Choosing Rust is itself increasingly a security-architecture decision — the "eliminate the bug class" lever, one level up from any middleware.
