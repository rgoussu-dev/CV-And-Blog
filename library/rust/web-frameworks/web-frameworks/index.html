    Rust web frameworks — the landscape

    # How the tower/hyper substrate shapes the field — Axum as the Tokio-native default, Actix Web's own stack, Rocket's ergonomics-first lineage, and the smaller players.

    Conceptsaved 2026-08-09 #rust#frameworks#web#http#axum#actix#rocket

    Overview

    Rust's web ecosystem sits between its neighbours' models: no production HTTP server in the standard library (unlike Go), but no framework-owned universes either (unlike the JVM). Instead there is a shared substrate — hyper for the HTTP engine, tower for the Service abstraction, the http crate for types — and the frameworks differentiate by how they relate to it. Axum, maintained by the Tokio team, is the substrate with ergonomics on top and has become the community default. Actix Web predates that consensus and ships its own HTTP stack — fast, mature, self-contained. Rocket, the ergonomics pioneer, sits apart with its own idioms and a smaller orbit. Everything runs on Tokio.

    Key points

    • The substrate is the spec: tower::Service — a trait for async request → response functions — plays the role Go's http.Handler and Jakarta's servlet contract play elsewhere: whoever honors it inherits an ecosystem of middleware (tower-http: trace, compression, CORS, auth, timeouts) for free. Who honors what: the correspondence table.
    • hyper is the shared engine: HTTP/1 and /2 (h3 via a sibling crate), used by axum, warp, reqwest, tonic and half the ecosystem; its 1.0 release (2023) froze the contract the stack builds on.
    • Axum is the default recommendation: routing + extractors over hyper, tower-native end to end, no macros for handlers — deep dive: Axum.
    • Actix Web is the performance-pedigreed incumbent: its own actix-http engine and middleware model, top of every benchmark for years, actor heritage now mostly vestigial — deep dive: Actix Web.
    • Rocket is the ergonomics-first outlier: attribute-macro routing, request guards, batteries included, a Rails-flavoured developer experience that predates async Rust — deep dive: Rocket.
    • The second shelf: warp (filter combinators over hyper — powerful, cryptic types; axum absorbed its niche), poem (axum-like with OpenAPI first-class), salvo, and Loco (a Rails-clone convention layer over axum + sea-orm).
    • Default advice: Axum for new services (ecosystem gravity, tower interop, Tokio-team maintenance); Actix Web when its maturity or measured throughput matters; Rocket when its ergonomics win hearts and the service is self-contained.

    Comparison

    HTTP engine hyper own (actix-http) hyper (since 0.5)
    Middleware model tower Layer/Service — ecosystem-shared own Transform/middleware trait fairings (lifecycle hooks) + request guards
    Handler style plain async fns; extractors by argument type async fns + extractors; #[get("...")] macros optional attribute macros (#[get("/<id>")]), guards
    State State<T> extractor, typed web::Data<T> managed state (State<T>)
    Perf posture fast; benchmarks near actix historically the benchmark leader competitive since async 0.5
    Maintenance Tokio team community team (post-2020 relaunch) small team, slower cadence
    Sweet spot default; anything on the Tokio stack throughput-critical APIs, maturity DX-first apps, teaching, small services

    Contrast with Go and Java

    Go's stdlib-first culture makes frameworks optional ergonomics (the landscape); Java's spec culture makes them competing platforms (the landscape). Rust landed on a third shape: a community-owned substrate (tower/hyper — de-facto, not specified) with thin frameworks over it, plus pre-substrate incumbents. The axum-vs-actix question is thus really "shared contracts vs self-contained stack" — Go's chi-vs-Fiber question, one level up.
