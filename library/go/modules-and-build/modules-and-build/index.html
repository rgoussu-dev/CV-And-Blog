    Modules & the Go build ecosystem

    # Go's single first-party build path — the go command plus modules — and the artifact formats and module ecosystem around it.

    Conceptsaved 2026-08-09 #go#build#tooling#packaging#modules

    Overview

    Where Java offers a three-way build world (bare JDK tools, Maven, Gradle — see The Java build ecosystem), Go ships exactly one first-party path: the go command with modules. Compilation, dependency resolution, testing, vetting, and installation are all subcommands of one tool, and the module system is part of the toolchain rather than a separate package manager. External build systems only enter the picture at monorepo scale, and task runners only for orchestration around the go command — never as a replacement for it.

    Key points

    • One tool: go build, go test, go mod, go install cover what Maven/Gradle plus a package manager cover elsewhere; there is no community debate about which build tool to use — see The go command & tool catalog.
    • Modules are the only dependency story since Go 1.16 made them the default: a go.mod per module, versions resolved by Minimal Version Selection — deep dive in Go modules.
    • Monorepo-scale exceptions: Bazel with rules_go + Gazelle (BUILD-file generation from Go sources), and Please, appear where hermetic caching across many languages pays for their complexity. They wrap the Go compiler; they do not replace modules' semantics.
    • Task runners orchestrate, never build: Make and Task (Taskfile.yml) commonly wrap go build/go test invocations, lint, and release steps — thin glue, not a build system.
    • The default artifact is a static binary: cross-compiled with GOOS/GOARCH env vars, no runtime to install — the inverse of the JVM's fat-jar-plus-runtime model.
    • Release engineering (reproducibility, cross-compilation matrices, GoReleaser, containers) is its own craft — see Building & releasing.

    Details

    Artifact formats

    Format Produced by Notes
    Static binary go build (default) One self-contained executable per GOOS/GOARCH; no interpreter, no runtime install. Contrast the JVM's jar + runtime split
    c-archive / c-shared go build -buildmode=c-archive|c-shared Static/shared library plus C header for embedding Go in C/other hosts; crosses the cgo boundary
    Plugin go build -buildmode=plugin Loadable .so via plugin package; Linux/macOS only, must match toolchain and dependency versions exactly — rarely used in practice
    WASM GOOS=js GOARCH=wasm or GOOS=wasip1 GOARCH=wasm Browser and WASI targets; large binaries from the stock compiler — TinyGo for small ones
    Container image Multi-stage Dockerfile, FROM scratch/distroless, or ko The static binary makes near-empty base images practical; ko builds and pushes images without a Dockerfile

    The module ecosystem

    There is no Maven-Central-style hosting step. A module's identity is its VCS path (github.com/user/repo), publishing is tagging a commit, and the module proxy (proxy.golang.org) fronts the world's VCS hosts with an immutable cache and checksum transparency. The consequence: no upload accounts, no namespace registry — and availability depends on the proxy, not on the original host staying up. Mechanics in Go modules.
