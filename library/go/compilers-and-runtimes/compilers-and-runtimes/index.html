    Go compilers & runtimes compared

    # The Go specification versus its implementations — the gc reference toolchain, gccgo, gollvm, TinyGo — and the WASM targets.

    Conceptsaved 2026-08-09 #go#runtime#compilers#gc#wasm

    Overview

    Like Java, Go separates a language specification from its implementations — but the ecosystem looks nothing like the JVM's. One implementation, the gc toolchain shipped with every Go release, is utterly dominant: it is the reference, it defines what "current Go" means, and its runtime choices (scheduler, GC) are what people mean when they talk about "how Go behaves". The alternatives — gccgo, gollvm, TinyGo — exist for specific niches, not as competing general-purpose runtimes the way HotSpot, OpenJ9 and Zing compete (contrast JVM implementations compared).

    Key points

    • Spec vs implementation: the Go spec fixes syntax, types and semantics; goroutine scheduling and GC behaviour are gc-implementation detail, not language guarantees.
    • gc: the reference toolchain — compiler written in Go, SSA backend, AOT compilation to static binaries, no JIT; the defining trade against the JVM.
    • The runtime is linked in: every gc binary embeds the G-M-P scheduler, the tri-colour concurrent GC and the netpoller — there is no separate VM to install.
    • gccgo / gollvm: the same GCC-maintained frontend on GCC and LLVM backends; occasionally better codegen, chronically behind the spec, niche.
    • TinyGo: an LLVM-based compiler for microcontrollers and WASM — a genuinely different runtime story; see the deep dive.
    • WASM is a first-class gc target: js/wasm for browsers, wasip1 for runtimes; TinyGo produces far smaller modules where size matters.
    • No TCK equivalent: conformance is pragmatic — the spec plus the standard library's behaviour as implemented by gc is the de facto contract.

    Details

    The Go specification

    The Go Programming Language Specification is deliberately compact — around a hundred pages, short enough to actually read end to end, and that compactness is treated as a feature to defend: proposals are routinely rejected for the spec complexity they would add. It fixes syntax, the type system (including generics since 1.18 and range-over-func iterators since 1.23), declaration and scoping rules, expression and statement semantics, and the built-in types' behaviour. A companion document, the Go Memory Model, defines the happens-before guarantees for concurrent programs — revised in 2022 to align with C++/Java-style data-race semantics ("programs with data races are invalid").

    Equally important is what the spec leaves open: how goroutines are scheduled, how the garbage collector behaves, stack growth, the pacing knobs (GOGC, GOMEMLIMIT) — all gc-implementation detail. Code that depends on scheduling order or finalizer timing is depending on an implementation, not on Go. Saved reference: The Go spec.

    gc — the reference toolchain

    The gc toolchain (cmd/compile, historically "gc" for Go compiler, nothing to do with garbage collection) ships with every release and is self-hosted: written in Go since 1.5. The compiler lowers to a generic SSA form and runs a portable optimisation pipeline — escape analysis (deciding which values may live on a goroutine stack instead of the heap), inlining, bounds-check elimination, devirtualisation — before architecture-specific lowering. Since 1.21, profile-guided optimisation can feed a production CPU profile back into inlining and layout decisions.

    The runtime linked into every binary provides:

    • G-M-P scheduler — goroutines (G) multiplexed onto OS threads (M) via per-core processors (P); work-stealing, and asynchronous preemption since 1.14 so tight loops cannot starve the scheduler.
    • Tri-colour concurrent GC — a non-generational, non-compacting concurrent mark-sweep collector with very short stop-the-world phases, paced by GOGC and capped by GOMEMLIMIT (1.19).
    • Netpoller — network I/O integrated with the scheduler over epoll/kqueue/IOCP, so a blocked read parks the goroutine, not the thread.

    There is no JIT and never has been: gc compiles ahead of time to a statically linked native binary. That is the defining trade against the JVM — instant start-up, trivial deployment, predictable memory, in exchange for no runtime re-optimisation based on live profiles (PGO recovers some of it, offline).

    gccgo & gollvm

    gccgo is a Go frontend for GCC, maintained in the GCC tree and sharing its "gofrontend" with gollvm. It benefits from GCC's mature middle-end — on some CPU-bound numeric code it produces better machine code than gc — and reaches architectures gc does not support. The costs: it trails the spec by releases (generics support arrived long after 1.18), its runtime lags, and escape analysis differs. gollvm puts the same frontend on LLVM; it has always been experimental and development is largely dormant. Both are niche answers — "I need GCC's platforms or codegen" — not alternatives you reach for by default.

    TinyGo

    TinyGo compiles a subset of Go via LLVM for places the standard runtime cannot go: microcontrollers with kilobytes of RAM, and WASM where a multi-megabyte module is unacceptable. It swaps the runtime story entirely — selectable GC (including none), aggressive dead-code elimination, goroutines on bare metal — at the price of stdlib and reflection gaps. Full treatment: TinyGo deep dive.

    WASM targets

    gc has targeted GOOS=js GOARCH=wasm since 1.11 (browser execution via the wasm_exec.js shim and syscall/js for DOM interop) and GOOS=wasip1 since 1.21 (WASI preview 1, for server-side runtimes like wazero, Wasmtime and Wasmer). gc modules carry the full runtime — typically a couple of megabytes upwards even compressed — which is fine for an application, painful for a plugin. TinyGo's output is often one to two orders of magnitude smaller, which is why it dominates the WASM-plugin and proxy-filter space.
