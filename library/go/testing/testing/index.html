    Testing in Go — strategies & tooling map

    # Map of Go testing strategies — unit to security — built on the stdlib testing package, with tools and deep-dive links per strategy.

    Conceptsaved 2026-08-09 #go#testing#tooling#quality

    Overview

    Go ships its testing substrate in the standard library: the testing package plus go test cover unit tests, benchmarks and fuzzing with no framework at all, and net/http/httptest makes integration-grade HTTP tests nearly as cheap as unit tests. Everything else — containers, browsers, mutation, load — layers third-party tools on top of that same substrate. This note maps the strategy axes onto the tools worth knowing and hands off to a deep-dive note per strategy.

    Key points

    • The stdlib testing package is the substrate: every tool below — testify, gomock, testcontainers-go, rapid, even the fuzzer — plugs into func TestXxx(t *testing.T) and runs under go test. One runner, one build/IDE integration, no engine to choose.
    • Table-driven tests are the idiom: a slice of cases plus t.Run subtests is Go's answer to parameterized tests; reach for it before any abstraction.
    • House position — integration is cheap in Go: httptest.Server runs your real handlers on a real socket in-process, so "test through the HTTP boundary" costs milliseconds; the pyramid flattens accordingly for glue-heavy services.
    • Assertions are a debate, not a given: testify is ubiquitous; the purist stack is plain if + go-cmp. Pick one per repo and stay consistent.
    • Coverage is a floor: go test -cover says what ran; mutation testing (gremlins) says what was asserted — younger tooling than the JVM's, use it selectively.
    • Fuzzing is native since Go 1.18: f.Fuzz with corpus management is in the toolchain; property-based testing (rapid) is the complementary third-party technique.
    • Performance and security are testing concerns: testing.B + benchstat and govulncheck + gosec belong in the same portfolio and the same CI.

    Details

    Strategy → tools → deep dive

    Strategy What it verifies Standard Go tools Deep dive
    Unit One behaviour in isolation, milliseconds testing (table tests, subtests), testify or go-cmp, hand-rolled fakes, gomock/mockery Unit testing
    Integration Code + real dependencies (DB, broker, HTTP) httptest, testcontainers-go, dockertest Integration testing
    End-to-end The deployed system through its public surface plain net/http clients, playwright-go/rod/chromedp, pact-go for contracts End-to-end testing
    Mutation Quality of the test suite itself gremlins, go-mutesting Mutation testing
    Property-based & fuzzing Invariants over generated inputs; crashes on hostile input rapid (gopter legacy); native go test -fuzz Property-based testing & fuzzing
    Performance Latency/throughput of code and system testing.B + benchstat (micro), vegeta/k6/hey (load) Performance & load testing
    Security Known vulns, insecure code, supply chain govulncheck, gosec, fuzzing, trivy/grype Security testing

    Choosing the boundary

    • Pure domain logic → table-driven unit tests, no doubles beyond your own interfaces.
    • HTTP handlers and middleware → httptest against the real mux; mocking the router proves nothing. This is Go's sweet spot — use it liberally.
    • Persistence/messaging glue → testcontainers-go against the real engine; segregate with -short or build tags so the fast loop stays fast.
    • Cross-service behaviour → consumer-driven contracts (pact-go) over broad E2E; keep a thin smoke layer of true E2E for deployment confidence.
    • Suite trustworthiness → run gremlins on the packages where correctness matters most.
