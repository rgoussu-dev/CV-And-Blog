    Security in Go applications — the map

    # How the recurring security concerns map onto Go's stdlib and de-facto libraries, composed as middleware rather than a framework.

    Conceptsaved 2026-08-09 #go#security#frameworks#middleware

    Overview

    Go has no Spring Security — no single framework owning authn, authz, CSRF and headers behind one configuration DSL. Instead the standard library supplies unusually strong primitives (crypto/*, crypto/tls, html/template) and each concern is solved by composing a small, well-known library as net/http middleware. That is both the posture and the risk: nothing is on by default, so the concern → library map must be assembled deliberately per service. This note is that map; general theory lives in the Security theme, the contrast in Security in Java applications.

    Key points

    • Authn/authz are separate middlewares: identity established by a token-validating or session-loading handler wrapper; permissions enforced in-handler or by a policy engine — casbin for in-process RBAC/ABAC models, OPA for externalised Rego policy.
    • OAuth2/OIDC is the default perimeter: golang.org/x/oauth2 for the client side, coreos/go-oidc for discovery and ID-token/JWT verification — see OAuth2 & OIDC in Go.
    • The web attack surface is handled piecemeal: database/sql parameterisation, html/template contextual escaping, gorilla/csrf, rs/cors, unrolled/secure for headers — see Web security in Go apps.
    • Crypto is stdlib-first and misuse-resistant: AEAD-oriented crypto/*, modern crypto/tls defaults, golang.org/x/crypto for argon2/bcrypt — see Cryptography in Go.
    • Secrets come from the environment, hashicorp/vault/api or cloud KMS SDKs; nothing in-language.
    • Supply chain is comparatively strong: module checksums (go.sum + sumdb), reproducible builds, call-graph-aware govulncheck — see Security testing.
    • No framework defaults means no safety net: a forgotten middleware fails silently open, so a per-service checklist (or a shared internal middleware stack) substitutes for what Spring auto-configures.

    Go as security infrastructure

    A useful asymmetry: while Go applications compose their security from libraries, much of modern identity and policy infrastructure is itself written in Go — Ory (Hydra/Kratos/Fosite), Zitadel, Dex, HashiCorp Vault, OPA. Practically this means the reference implementations you integrate against are readable Go code, embeddable as libraries (Fosite, OPA), and cheap to run in integration tests. Scanning for the concerns above lives in Security testing.
