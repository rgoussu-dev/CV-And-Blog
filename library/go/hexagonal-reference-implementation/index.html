    Hexagonal architecture reference implementation — Go

    # The house hexagonal reference realized for Go — one module per service, cmd/ binaries as deployment units, ports at the consumer, nested internal/ walls, and explicit constructor wiring with wire as the sanctioned escalation.

    Conceptsaved 2026-08-09 #hexagonal-architecture#architecture#go#packages#reference-implementation

    Overview

    The house reference implementation of hexagonal architecture for Go, standing on its own terms. The shared principles live in that note — trisection, one deployment unit per primary adapter, a contract face and an implementation face for the domain, containerisation beside its unit, README.md/AGENTS.md at every level. Go's realization builds the walls from what the language gives: a service is one Go module, packages don't declare dependency rules, so nested internal/ visibility holds the wall that matters most and an import linter holds the softer rules. Settled as the house reference (2026-08-09 discussion).

    Key points

    • One Go module per service; one cmd/<unit>/ per deployment unit. Each primary adapter gets a cmd/ binary — cmd/rest-public/, cmd/rest-backoffice/, cmd/grpc-server/, cmd/kafka-consumers/, cmd/cron-jobs/ — with its Dockerfile beside its main.go. Multi-module workspaces inside one service buy a hard module graph at a real toolchain cost; not the default.
    • The domain is one package tree with two faces. Go defines interfaces at the consumer, and for driven ports the consumer is the domain, so ports live in the domain package by design: the contract face is internal/domain/ (ports, commands, events, factories), the implementation face is internal/domain/internal/… — package layout, not separate artifacts.
    • The core stays compiler-hidden via nested internal/. internal/ visibility is directory-scoped: packages under internal/domain/internal/… are importable only from within the internal/domain subtree. Ports, commands, events and exported factory functions live in internal/domain/; entities and domain services live in internal/domain/internal/…. A main.go physically cannot import the core — it calls domain.NewPlaceOrder(repo, billing) and receives the driving-port interface. That is the Maven wall, rebuilt from a visibility rule and the constructor-returns-interface idiom.
    • Primary adapters live in internal/app/<adapter>/ (handlers, mappers, server setup); their transport contracts (generated OpenAPI types, protobuf stubs, message schemas) live in api/ at the root when they're published to other teams. The contract artifact exists only where the contract is real (nothing for cron). Give api/ its own tiny go.mod when outside consumers exist, so they don't drag the service's dependency tree.
    • Secondary adapters live in internal/infra/<technology>/ (infra/postgres/, infra/kafka/, infra/billingclient/) — same granularity rule as Java: the unit's imports (and thus the linker) decide what ships in each binary; Go's dead-code elimination means an unimported adapter costs the binary nothing.
    • The assembly point is each main.go. Explicit constructor wiring, no DI framework: construct infra adapters, inject into domain constructors, hand driving ports to the transport server. Shared assembly helpers can live in internal/config/ when several binaries wire identical subsets.
    • Dependency injection is a pattern here, not a container — see the Details section for the settled stance: constructor injection at the composition root by default, wire as the sanctioned escalation, reflection containers (fx/dig) ruled out.
    • The linter covers only the softer rules. With the core compiler-hidden, what's left for depguard/go-arch-lint in CI: domain imports nothing from app/infra, infra never imports app, adapters never import each other. A go.work multi-module split to harden these too was considered and rejected: the toolchain friction (inter-module versioning, IDE, release tagging) outweighs walls the linter holds fine.

    The walls and what enforces them

    Rule Enforced by
    the domain core is invisible to adapters and mains nested internal/: everything under internal/domain/internal/ is unimportable outside the domain subtree — the compiler
    domain imports nothing from app/infra; infra never imports app; adapters never import each other depguard/go-arch-lint in CI, plus review
    a deployment unit ships only what it uses the unit's main import list (the ops runbook) + dead-code elimination
    published contracts don't drag the service's dependencies api/ with its own tiny go.mod when outside consumers exist
    the assembly point stays boring plain main.go wiring; extract internal/config only on real duplication

    Dependency injection — pattern, not container (settled 2026-08-09)

    Go has DI the pattern — constructor injection at a composition root — not a DI container, and the reference embraces that:

    • Default: hand-written constructor wiring in each cmd/ main. Small consumer-side interfaces and constructor-returns-interface make the whole assembly a handful of plain lines the compiler fully checks. The language has no annotations, so a runtime container must lean on reflection — hidden object graph, wiring errors moved from compile time to startup — which is exactly what the culture (and this reference) rejects.
    • Sanctioned escalation: google/wire when mains grow painful. Compile-time code generation from the same provider functions you already have: it changes who types the wiring, not the architecture — the graph stays visible and errors stay at build time.
    • Ruled out: fx/dig. A runtime reflection container reintroduces startup-time resolution errors and an obscured graph, and blurs "the assembly point is main.go".

    Nothing left open

    The last question — where DTO↔command mapping helpers live when two transport adapters share shapes — is settled (2026-08-09): duplicate them. By design there should be scarcely any overlap between deployment units; the rare shared shape is cheaper as two copies than as a mapping package coupling units meant to evolve independently.

    Examples

    cmd/rest-public/main.go as the configurator:

    func main() {
    db := postgres.MustOpen(os.Getenv("DATABASE_URL"))
    orders := postgres.NewOrderRepository(db)      // driven adapter
    billing := billingclient.New(os.Getenv("BILLING_URL"))

    // factory exported from internal/domain: constructs the service hidden in
    // internal/domain/internal/order and returns the driving-port interface
    placeOrder := domain.NewPlaceOrder(orders, billing)

    srv := restpublic.NewServer(placeOrder)        // driving adapter ← driving port
    log.Fatal(http.ListenAndServe(":8080", srv))
}
