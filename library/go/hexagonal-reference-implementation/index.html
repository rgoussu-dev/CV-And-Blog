    Hexagonal reference implementation — Go derivation

    # Deriving the house hexagonal reference for Go — packages instead of modules, cmd/ binaries as deployment units, interfaces at the consumer, and the nested internal/ trick that keeps the domain core compiler-hidden.

    Conceptsaved 2026-08-09 #hexagonal-architecture#architecture#go#packages#reference-implementation

    Overview

    The Java reference realizes the house hexagonal principles with Maven modules as compile-time walls. Go has no equivalent intra-service module graph — a service is one Go module, and packages don't declare dependency rules — so the derivation keeps every principle (trisection, one deployment unit per primary adapter, contract/implementation split, colocated Dockerfiles, per-directory README.md/AGENTS.md) but changes the enforcement: nested internal/ visibility for the wall that matters most, an import linter for the softer rules — the module graph is not missed. Settled as the house derivation (2026-08-09 discussion).

    Key points

    • One Go module per service; one cmd/<unit>/ per deployment unit. Each primary adapter gets a cmd/ binary — cmd/rest-public/, cmd/rest-backoffice/, cmd/grpc-server/, cmd/kafka-consumers/, cmd/cron-jobs/ — with its Dockerfile beside its main.go. Multi-module workspaces inside one service buy Maven-like enforcement at a real toolchain cost; not the default.
    • domain-api vs domain-core collapses into one internal/domain/ package tree — and that is idiomatic, not a loss: Go defines interfaces at the consumer, and for driven ports the consumer is the domain, so ports live in the domain package by design.
    • The core stays compiler-hidden via nested internal/. internal/ visibility is directory-scoped: packages under internal/domain/internal/… are importable only from within the internal/domain subtree. Ports, commands, events and exported factory functions live in internal/domain/; entities and domain services live in internal/domain/internal/…. A main.go physically cannot import the core — it calls domain.NewPlaceOrder(repo, billing) and receives the driving-port interface. That is the Maven wall, rebuilt from a visibility rule and the constructor-returns-interface idiom.
    • Primary adapters live in internal/app/<adapter>/ (handlers, mappers, server setup); their transport contracts (generated OpenAPI types, protobuf stubs, message schemas) live in api/ at the root when they're published to other teams — the Go convention closest to Java's *-api modules, and the same rule applies: the contract artifact exists only where the contract is real (nothing for cron). Give api/ its own tiny go.mod when outside consumers exist, so they don't drag the service's dependency tree.
    • Secondary adapters live in internal/infra/<technology>/ (infra/postgres/, infra/kafka/, infra/billingclient/) — same granularity rule as Java: the unit's imports (and thus the linker) decide what ships in each binary; Go's dead-code elimination means an unimported adapter costs the binary nothing.
    • The configurator is each main.go. Explicit constructor wiring, no DI framework: construct infra adapters, inject into domain constructors, hand driving ports to the transport server. Shared assembly helpers can live in internal/config/ when several binaries wire identical subsets.
    • The linter covers only the softer rules. With the core compiler-hidden, what's left for depguard/go-arch-lint in CI: domain imports nothing from app/infra, infra never imports app, adapters never import each other. A go.work multi-module split to harden these too was considered and rejected: the toolchain friction (inter-module versioning, IDE, release tagging) outweighs walls the linter holds fine.

    Details

    The derived tree

    acme-service/
├── README.md / AGENTS.md
├── go.mod
├── cmd/
│   ├── rest-public/       # main.go + Dockerfile  ← deployment unit
│   ├── grpc-server/
│   ├── kafka-consumers/
│   └── cron-jobs/
├── api/                   # published contracts: openapi/, proto/, schemas/
├── internal/
│   ├── domain/            # ports, commands, events, factories — the contract face
│   │   └── internal/
│   │       └── order/     # entities, services — compiler-hidden core face
│   ├── app/
│   │   ├── restpublic/    # handlers + DTO↔command mapping
│   │   ├── grpcserver/
│   │   ├── kafkaconsumer/
│   │   └── cron/
│   ├── infra/
│   │   ├── postgres/
│   │   ├── kafka/
│   │   └── billingclient/
│   └── config/            # optional shared wiring helpers
├── compose.yaml
└── deployment/            # OpenTofu, same shape as the Java reference

    What the derivation gives up, and the mitigation

    Java mechanism Go reality Mitigation
    Maven graph forbids infra → domain-core packages don't declare dependency rules nested internal/: the core under internal/domain/internal/ is unimportable outside the domain subtree — compiler-enforced
    domain-api artifact consumed by clients no intra-service artifacts published contracts live in api/; domain ports stay internal
    per-unit dependency list = ops runbook one go.mod for the service each cmd/ main's import list is the runbook; DCE keeps binaries lean
    configurator module plain main.go wiring keep mains boring; extract internal/config only on real duplication

    Nothing left open

    The last question — where DTO↔command mapping helpers live when two transport adapters share shapes — is settled (2026-08-09): duplicate them. By design there should be scarcely any overlap between deployment units; the rare shared shape is cheaper as two copies than as a mapping package coupling units meant to evolve independently.

    Examples

    cmd/rest-public/main.go as the configurator:

    func main() {
    db := postgres.MustOpen(os.Getenv("DATABASE_URL"))
    orders := postgres.NewOrderRepository(db)      // driven adapter
    billing := billingclient.New(os.Getenv("BILLING_URL"))

    // factory exported from internal/domain: constructs the service hidden in
    // internal/domain/internal/order and returns the driving-port interface
    placeOrder := domain.NewPlaceOrder(orders, billing)

    srv := restpublic.NewServer(placeOrder)        // driving adapter ← driving port
    log.Fatal(http.ListenAndServe(":8080", srv))
}
