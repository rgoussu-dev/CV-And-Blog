    The Go toolchain

    # The single go command as the entire build system — distribution, environment, and the catalog of built-in and companion tools.

    Conceptsaved 2026-08-09 #go#tooling#build

    Overview

    Go ships its entire build system as one binary: go. Compiling, running, testing, dependency management, formatting, vetting, code generation, docs, profiling — all subcommands of the same tool, with zero project configuration beyond go.mod. This is a deliberate contrast to the JVM world, where the JDK provides compiler and diagnostics but every project bolts on Maven or Gradle for the actual build; in Go there is no separate build-tool layer to choose, configure, or fight.

    Key points

    • One command, whole lifecycle: go build/run/test/mod/vet/fmt/doc/generate/work/tool — the same interface on every Go project ever; no per-project build scripts to learn.
    • One archive to install: the distribution is a single tarball unpacked to GOROOT (compiler, standard library, go command). No plugin ecosystem, no version manager strictly needed.
    • Toolchain auto-switching (1.21+): go.mod can carry a toolchain go1.22.x directive; a newer-than-installed requirement makes the go command download and re-exec the exact required toolchain — reproducible builds without asking developers to upgrade in lockstep.
    • go env is the configuration surface: prints/sets the variables the toolchain reads; go env -w persists them to a config file rather than the shell.
    • GOPATH is residual: since modules it no longer scopes your code; it only locates the module cache (GOPATH/pkg/mod) and go install binaries (GOPATH/bin).
    • GOOS / GOARCH select the target platform per invocation — cross-compilation is an environment variable, not a separate toolchain install.
    • CGO_ENABLED toggles the C interop layer; 0 yields fully static pure-Go binaries and is the default when cross-compiling.
    • GOFLAGS injects default flags into every go invocation (e.g. -mod=vendor, -trimpath) — useful in CI images.
    • Not everything is a subcommand: the ecosystem's few essential externals (delve, gopls, staticcheck, govulncheck) install with go install and follow the same conventions.

    Details

    Tool catalog

    Purpose Tool What it does
    Build & run go build / run / install Compiles packages and binaries; build cache, tags, ldflags, cross-compilation, PGO
    Build & run go test Compiles and runs test binaries; selectors, cache, race detector
    Dependencies go mod Manages go.mod/go.sum: init, tidy, download, why, vendor
    Quality & formatting gofmt & goimports Canonical formatting and import management — no configuration, no debates
    Quality & formatting go vet Shipped static analyzer for likely-wrong code; runs under go test
    Quality & formatting go tool cover Coverage profiles, HTML annotation, per-function summaries
    Docs go doc & pkgsite Doc comments to terminal docs and pkg.go.dev rendering
    Generate & workspaces go generate Runs //go:generate directives — explicit, committed code generation
    Generate & workspaces go work Multi-module workspaces for local cross-module development
    Profiling & tracing pprof CPU/heap/goroutine profiles, flame graphs, net/http/pprof
    Profiling & tracing execution tracer Nanosecond-scale runtime event traces: scheduling, GC, blocking
    Debugging delve The Go debugger: breakpoints, goroutine inspection, core dumps
    Editor & lint gopls The official LSP server behind every serious Go editor setup
    Editor & lint staticcheck & golangci-lint The de-facto linters beyond vet
    Vulnerability govulncheck Call-graph-aware scanning against the Go vulnerability database

    The first block is what you type daily; the externals in the lower half install via go install and are standard on any professional team.
