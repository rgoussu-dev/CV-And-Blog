    Backend protocols in Go — the map

    # How REST, GraphQL, gRPC, WebSockets/SSE and messaging map onto Go's stdlib and the dominant community libraries.

    Conceptsaved 2026-08-09 #go#protocols#frameworks#api-design

    Overview

    Go's protocol story is lopsided by design: HTTP is covered deeply by the standard library (net/http is a production-grade server and client, not a toy), while every other protocol lives outside the stdlib with one dominant community library and a handful of credible alternatives. There is no Jakarta-style spec layer and no framework indirection — you pick the library, import it, and its API is the integration. That makes the map below shorter than the JVM equivalent but makes knowing the de-facto choice per protocol more important, because there is no standard to fall back on.

    Key points

    • stdlib covers HTTP deeply: server, client, HTTP/2, TLS, and since 1.22 method + wildcard routing in ServeMux — many services ship REST APIs with zero third-party routing dependencies.
    • Everything else has a de-facto library: gqlgen for GraphQL, grpc-go for gRPC, gorilla/websocket for WebSockets, franz-go or kafka-go for Kafka, nats.go for NATS. Community consensus substitutes for a spec.
    • Sync vs async: REST, GraphQL and unary gRPC are request/response; messaging decouples in time; WebSockets/SSE and gRPC streams hold connections open. Goroutines make the long-lived-connection cases unusually cheap in Go.
    • Text vs binary: JSON via encoding/json (REST, GraphQL) is debuggable; protobuf (gRPC) and Avro (Kafka) are compact and schema-enforced but need tooling.
    • Contract location: REST documents after the fact (OpenAPI, via codegen tools); GraphQL and gRPC are schema-first by construction; messaging contracts live in a schema registry if anywhere. The doc tooling per framework has its own note: API documentation in Go.
    • Codegen is the idiom: where Java leans on annotations and reflection, Go leans on code generation — gqlgen, protoc-gen-go/buf and oapi-codegen all emit plain Go you can read and debug.
    • Each deep dive below names the concrete libraries — that mapping is the point of this group.

    Details

    The protocol × library matrix

    Protocol stdlib support De-facto library Notable alternatives Deep dive
    REST / HTTP APIs Full: net/http server + client, 1.22 ServeMux patterns, encoding/json chi (or bare stdlib) for routing; oapi-codegen for OpenAPI gin, echo, fiber; huma, fuego (OpenAPI-native) REST
    GraphQL None gqlgen (schema-first codegen) graphql-go/graphql, graph-gophers/graphql-go GraphQL
    gRPC None (HTTP/2 in stdlib underneath) grpc-go + buf toolchain connect-go, grpc-gateway gRPC
    WebSockets / SSE SSE yes (flusher pattern); WebSocket no gorilla/websocket coder/websocket, melody WebSockets & SSE
    Messaging (Kafka / NATS / AMQP) None franz-go or segmentio/kafka-go (Kafka); nats.go (NATS); amqp091-go (RabbitMQ) IBM/sarama, confluent-kafka-go; watermill as abstraction Messaging

    Choosing

    Default to REST on net/http for public and browser-facing APIs; GraphQL when clients need flexible aggregation and you can afford the schema machinery; gRPC for internal service-to-service calls where streaming, latency or polyglot contracts matter; WebSockets/SSE when the server must push (and prefer SSE when one-directional suffices); messaging whenever the work can be asynchronous. NATS deserves a special mention: it is a Go-native ecosystem citizen the JVM world rarely reaches for, and often the lightest-weight async option in an all-Go shop.
