    Storage access from Go — the map

    # How Go reaches every storage kind — database/sql, per-store drivers, and the raw-driver-to-ORM spectrum, mapped store by store.

    Conceptsaved 2026-08-09 #go#storage#databases#drivers

    Overview

    Go's storage story is thinner and flatter than the JVM's, deliberately. The stdlib gives one abstraction — database/sql, a pooled, driver-agnostic interface for relational stores — and everything else is a vendor or community client library speaking the store's wire protocol directly. There is no JPA equivalent and no framework data layer: no container manages entities for you, and the mainstream idiom is closer to the metal. The real decision per store is which driver to use and how much query/mapping machinery to stack on top of it.

    Key points

    • database/sql is the only stdlib abstraction, and it covers relational only. It buys driver portability and a built-in connection pool at the cost of a lowest-common-denominator API — which is why the Postgres world often bypasses it for pgx's native interface.
    • Every non-relational store is a direct client: go-redis, mongo-go-driver, gocql, neo4j-go-driver. Each exposes its own pooling, contexts, and consistency knobs; there is no common repository idiom to hide behind.
    • No ORM culture the way the JVM has one. The spectrum runs raw driver → sqlx (struct scanning) → sqlc (SQL-first codegen, the community darling) → ent/GORM (full ORM). Most teams stop well before the ORM end; SQL-in-the-open is the default aesthetic.
    • Contexts everywhere: every decent client takes a context.Context per call for timeouts and cancellation — the moral equivalent of JDBC statement timeouts, but explicit and composable.
    • Transactions are explicit values (*sql.Tx, pgx.Tx, driver session objects) passed through call chains — no @Transactional proxy magic, so demarcation is visible in the code.
    • Testing is Testcontainers-shaped here too: real store, real driver, in CI — same substrate as the Java stack.

    Choosing an entry point

    • Debugging connectivity, pool exhaustion, or timeouts → the driver layer; there is no framework above it to hide the problem, which is a feature.
    • Query-heavy relational work → decide the sqlc vs sqlx vs ORM question early; it shapes the whole repository layer. The web framework you chose barely matters here — handlers call the same storage code whichever router is in front (web frameworks).
